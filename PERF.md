# PERF.md — the measured numbers, and the conditions they were measured under

Every number in this file was produced by `just bench` and `just compare` on the machine
described below, and the raw JSON is in `bench-results/`. Nothing here is estimated, extrapolated
or carried over from another machine.

**The tables below are derived, not typed.** The engine's comparison table is the median of
three full `just compare` runs, and the derivation is a checked-in script:

```bash
python3 scripts/medians.py
```

All three raw reports are committed, so the published figures can be re-derived by a reader
without re-running a benchmark. See [`bench-results/README.md`](bench-results/README.md).

**This set replaced a slower one, and the machine is the reason.** The set published before this one was
measured while the machine had **3.3 GB of swap in use** and **9 GB of memory compressed** by other
work on the same box, and the repository's own performance gate reported every kernel flavour
**46–53% slower** than its stored baseline while that campaign ran. This campaign ran with the gate
back **at** its baseline — the gate measures `cpp-simd` at 8.628 G rows/s against a stored baseline
of 8.306 G, and `scalar` at 3.532 G against 3.469 G — and every absolute figure in this file is
**about 40% faster** than the set it replaces, because all four systems were measured together, in
the same session, on a machine that was no longer thrashing.

What the change does **not** do is move the comparisons: every table here measures the engine and
every incumbent at the same moment, on the same file, at the same thread count, so the *ratios* are
the machine's state divided out. And the fix this set measures is measured **back to back**, with the
two batch sizes alternating round by round, so that the machine's drift cannot bias it — see
[§3j](#3j-the-row-group-count-and-what-it-costs). Where a published number moved, both numbers are
given and the reason is named.

**Benchmark numbers are not portable between architectures.** These are AArch64 numbers. The
x86-64 / AVX2 **absolute** numbers do not exist and are not published — a GitHub-hosted runner is a
shared machine — but the x86-64 **ratios** now are, **per processor**: see
[§1b](#1b-the-kernel-on-x86-64-measured-natively). The two sets are never compared with each other.
The AVX2 path's *correctness* is verified on this machine as well: see
[AVX2 correctness](#avx2-correctness-verified-on-an-arm64-mac) below.

**This machine is shared, and it shows.** The *eager* figures spread the widest, because the eager
path reads 231 MiB and every stall in that read lands in the number; the *lazy* figures are the
tightest. DuckDB and Polars are separate processes on a busy machine, so their spreads are their
own. Where the document quotes a spread, quote it from the derivation.

**Every figure in this file is from this set**, and the comparison is like-for-like within it:
every system was measured on the same file, on the same machine, in the same three campaigns.

## 1. The comparison kernel

**What is measured:** one pass over a column of `f64` values, comparing every row against a
threshold and writing a bit mask. 20,000,000 rows, column `l_discount`, operator `>=`,
threshold `0.04`. **The median of six campaigns**, each the median of eight iterations.

### Two baselines, not one

| flavor | what it is | rows/sec | ns/row | vs scalar | vs cpp-auto | matches |
|---|---|---|---|---|---|---|
| `scalar` | the C++ reference compiled with `-fno-vectorize` | 3.42 G | 0.292 | 1.00× | 0.59× | 12,726,115 |
| `cpp-auto` | **the same source**, compiled with ordinary flags | 5.72 G | 0.175 | 1.70× | 1.00× | 12,726,115 |
| `cpp-simd` | the hand-written NEON kernel, over the C ABI | 8.37 G | 0.120 | 2.48× | **1.47×** | 12,726,115 |
| `rust-simd` | the Rust `std::arch` intrinsics kernel, no FFI | 8.29 G | 0.121 | 2.44× | 1.45× | 12,726,115 |

**The spread, because a benchmark that only publishes its best numbers is not a benchmark.** Over
the six campaigns: `scalar` 1.79–3.46 G, `cpp-auto` 5.34–5.88 G, `cpp-simd` 7.94–8.66 G,
`rust-simd` 7.79–8.49 G. This machine is not isolated, and **one campaign of the six ran with
its scalar baseline starved**: that campaign's scalar reference came in at 1.79 G while its
vectorised flavours ran at their usual speed, and the ratio against a starved baseline is what
stretches `cpp-simd`'s ratio out to 4.46×. The medians are the numbers to quote; the range is
the noise floor, and here the noise floor is the scalar reference's.

**These numbers moved, and the reason is the sample.** This table was one campaign of eight
iterations; it is now the median of six campaigns, which is the rule the rest of this file
follows. The medians moved by less than 5% — `scalar` 3.48 G → **3.42 G**, `cpp-auto` 5.75 G →
**5.72 G**, `cpp-simd` 8.73 G → **8.37 G**, `rust-simd` 8.72 G → **8.29 G** — and the ratios
moved with them: `cpp-simd` against the compiler's vectorisation **1.50× → 1.47×**, and against
the scalar reference **2.50× → 2.48×**.

**These numbers reproduce.** An earlier session measured the same kernel on the same machine and
got `scalar` 3.51 G, `cpp-auto` 5.87 G, `cpp-simd` 8.81 G, `rust-simd` 8.77 G — within 6% of the
medians above, and with the same two ratios to within 0.1×. Two independent sets agreeing to a
few percent is a stronger claim than either set alone.

Every flavor agrees on the match count, and the differential tests compare the **masks bit for
bit**, not just the counts.

### What the two ratios mean

- **`scalar → cpp-simd` is 2.48×.** This is how much vectorisation is worth, measured against a
  reference that really is scalar. It is checked against the disassembly: the `-fno-vectorize`
  object contains **zero** vectorised loop instructions, and the ordinary object contains ~300.
- **`cpp-auto → cpp-simd` is 1.47×.** This is the one that decides whether the hand-written kernel
  earns its complexity: it beats what clang produces from the same loop by nearly half.

The first version of this table published one ratio, against a baseline that clang had
auto-vectorised. It was measuring two vectorised implementations. See
[ADR-0006](docs/adr/0006-auto-vectorised-baseline.md).

### The FFI seam

`cpp-simd` crosses a C ABI; `rust-simd` does not. They are within **1.0%** of each other — 8.37 G
against 8.29 G — against a run-to-run spread of a few percent. The seam is free. See
[ADR-0003](docs/adr/0003-cpp-ffi-seam.md).

### AVX2 correctness (verified on an ARM64 Mac)

**This is not a performance claim.** It is the answer to "this machine has no AVX2", and the answer
turned out to matter more than expected.

The project has two SIMD paths: NEON, measured above on this machine, and AVX2, for x86-64. The
development hardware is an ARM64 MacBook, so the AVX2 half could not be *timed* here — and, when
somebody finally tried to cross-build it, it turned out it could not be *compiled* either. The
AVX2 Rust intrinsics path had never been built by anyone. It had two type errors in it (`u32`
accumulated into a `u64` mask), and it had been sitting in the tree, unchecked, for the entire life
of the project. See [ADR-0009](docs/adr/0009-avx2-without-x86-hardware.md).

The fix has two halves.

**Compilation** is now gated. `just check-x86` cross-compiles the workspace for
`x86_64-apple-darwin` on this machine, and CI runs the same check. The AVX2 path cannot rot
unnoticed again.

**Correctness** is now testable here, because Rosetta 2 executes AVX2 instructions correctly on
Apple Silicon while reporting *no* AVX2 in CPUID — the host is an ARM64 chip, so the feature bits
say so. The kernel's runtime probe therefore correctly concludes that there is no AVX2 path and
never enters it. `COLUMNAR_FORCE_SIMD=avx2` overrides the probe, which is what `just verify-avx2`
does:

```
$ just verify-avx2

-- without the override --
    forced        : auto
    simd_kind     : none
    avx2 rows     : 0
    matches oracle: true

-- with COLUMNAR_FORCE_SIMD=avx2 --
    forced        : avx2
    simd_kind     : avx2
    avx2 rows     : 1024
    matches oracle: true

RESULT: PASSED -- 3 test binaries green under Rosetta 2 with AVX2 forced.
```

The `avx2 rows` counter is the load-bearing part. A dispatch that *reports* the AVX2 path is not
proof that the path's instructions ran; the counter moves only if they did, and the mask it
produced is compared against the oracle's bit for bit. So the claim is narrow and specific: **the
AVX2 path — both the C++ FFI path and the Rust intrinsics path — compiles, executes, and produces
masks identical to the oracle's, on an ARM64 Mac.**

**What this does not establish: any AVX2 performance number.** Under Rosetta the instructions are
emulated, so a timing taken there measures the translator, not hardware. The benchmark harness
therefore *refuses to measure* while the override is in force — `just bench` exits with an
explanation rather than producing a number that means something other than what it appears to mean.
AVX2 timings require an x86-64 machine with AVX2, and are published only from one — the ratios are
in [§1b](#1b-the-kernel-on-x86-64-measured-natively), and what is still not published is in
[Not measured](#not-measured).

### 1a. The kernel in a browser

**This is a browser's number, and it is not a native number.** It is published here with everything
it depends on, and it is never compared with the native table in §1: a different runtime, a different
clock and a different compiler make the ratio between them a claim about two engines rather than
about one kernel. What the browser measures is the comparison it *can* make — the `simd128` path
against the oracle, over the same data, in the same process.

**What is measured**: one pass over a column of `f64` values, comparing every row against `0.04`
and writing a bit mask. 20,000,000 rows, five iterations per round, five rounds per campaign,
three campaigns.

| flavor | ns/row (median) | spread | rows/sec | matches |
|---|---|---|---|---|
| `oracle` | **3.414** | 3.398–3.426 | 0.293 G | 12,726,115 |
| `simd128` | **0.272** | 0.267–0.278 | 3.676 G | 12,726,115 |

**`simd128` is 12.59× the oracle**, over the three campaigns (12.56×–12.64×). The published set
before this one said **3.429** and **0.273** ns/row and **12.51×**; the figures moved by less than
1%, because the browser's number is the most stable one in the repository.

| | |
|---|---|
| browser | Chromium 148.0.7778.280, Electron 42.8.0, on macOS 27.0.1 |
| engine | `wasm32-unknown-unknown`, `simd128`, release build, fat LTO, one codegen unit |
| machine | Apple M4 Max, 14 cores — **the host's load average was 8.1–8.8 throughout** |
| warm-up | one untimed pass per implementation before each timed run |
| rounds | 5 per campaign, 3 campaigns, median published with the spread |
| commit | `e866e75` |

**The spread is published.** The host's load average was between 8.1 and 8.8 while these were
taken — the machine is shared and it was busy — and the oracle's range across the campaigns is
3.398–3.426 ns/row, a 0.8% range. The `simd128` path's is 0.267–0.278, a 4.1% range, and the
**ratio**'s is 12.56×–12.64×. A browser's numbers are the least portable thing this repository
publishes, and they are published with their spread for that reason.

**The masks are identical, bit for bit, in every campaign**, and so is the **edge check**: every
operator, a NaN value, a NaN threshold, the two zeros, the two infinities and a NULL row, against
the oracle. The page makes both checks itself, before it prints anything, so a reader who opens it
runs them too.

The match count is **12,726,115**, which is the native benchmark's number: the browser rebuilds
the benchmark's column from a histogram of the file's eleven distinct discount values, in an
interleaved order that is not the file's. The browser has no Parquet reader and does not pretend to
one.

The raw reports are committed — `browser-run1.json`, `browser-run2.json`, `browser-run3.json` — and
`python3 scripts/medians.py` derives the table above from them. See
[ADR-0019](docs/adr/0019-the-kernel-in-a-browser.md).

### 1b. The kernel on x86-64, measured natively

**This is the x86-64 half of §1, and it is published as ratios only.** The absolute rows/sec and
ns/row describe a GitHub-hosted runner — a shared machine whose load this repository neither
controls nor reproduces — so they are not published. The ratios are taken from four flavors
measured in the *same process, on the same machine, in the same run*, so the machine's state
divides out of them.

**And the machine is not one machine.** GitHub's hosted runners are a **fleet**: twenty-one runs
of the same workflow, on the same commit, with the same harness, landed on six different
processors. The ratio is a property of the **processor** as much as of the kernel, so it is
published **per processor**, and the processor is named.

| iterations | 8 per campaign, **3–11 campaigns** per processor |
| machine | GitHub-hosted `ubuntu-latest`, 4 cores, **1 thread**, Linux 6.17.0-1022-azure |

**The scalar baseline is the tell.** The 9V45 ran its scalar reference at **2.79 G rows/s** — twice
the 7763's 1.41 G — and it is the processor with the *smallest* AVX2 gain, 1.69× against 2.23×.
The hand-written kernel gains about as much in absolute terms on both; the *ratio* moves because
the denominator moves. A ratio published without the processor it was measured on is a number
about no machine at all, which is why the table above has a column for the processor.

**Three processors ran the campaign once each, and are not published.** They are the Intel Xeon
8370C, the Xeon 8573C and the Xeon 6973P-C, one campaign apiece, and this repository publishes
the median of at least three. One of them is the reason the rule exists: its single campaign
produced a ratio of **8.03×**, the highest number in this section — because that runner's scalar
baseline had been starved to 0.33 G rows/s, a tenth of the 9V45's. That is exactly the figure
this repository refuses to publish from one run on a machine nobody was measuring. It is named
here rather than quietly dropped, because a reader who saw it in a run's artifact should be told
why it is not in the table.

**This table is never compared with §1's.** A ratio measured on an M4 Max's NEON path and a ratio
measured on an EPYC's AVX2 path are two different measurements — different architecture,
different compiler, different machine — and setting them side by side would invite exactly the
comparison the numbers cannot support.

**What the x86-64 set does say is that the kernel is not an ARM64 story.** On three different
processors, on real x86-64 hardware, the hand-written AVX2 path is **1.7×–2.6× the scalar
reference** and **1.7×–2.6× the compiler's own vectorisation**, and the Rust `std::arch` path
lands within 10% of the C++ one. On ARM64 the two were within 1% of each other; here the Rust one
is 6–10% behind, which is the FFI seam's other side — it is not free in the same way.

The twenty-one raw reports are committed — `avx2-run-<run id>.json`, one per workflow run — and
`python3 scripts/medians.py` derives the table above from them, grouped by processor. The
workflow that produced them is `bench-avx2.yml`; the correctness job ran the differential suite
on native x86-64 hardware in the same dispatch. See
[ADR-0024](docs/adr/0024-the-repository-goes-public.md).

## 2. The engine, against DuckDB, Polars and DataFusion

Six queries, each measured twice: **resident** (the data is already in memory) and **cold** (the
Parquet file is read as part of the measurement). All three incumbents answer the same question in
the same mode, and every answer is cross-checked against the engine's.

The third incumbent is **new**: `DataFusion`, a Rust query engine reading the same Parquet through
the same Arrow stack. It is a separate cargo project under `tools/`, with its own committed lock
file, built by `just peer-build` — an **instrument, not a dependency**, so the engine's published
dependency graph does not move. See [ADR-0021](docs/adr/0021-the-materialised-column-and-a-rust-peer.md).

The queries:

| name | what it is |
|---|---|
| `scan` | `SELECT count(*)` over every row |
| `filter-numeric` | one numeric predicate, `l_discount >= 0.04` |
| `filter-string` | one predicate on the dictionary-encoded `l_shipdate` |
| `filter-range` | two numeric predicates `AND`ed, and a `SUM(l_quantity)` |
| `q6` | the TPC-H Q6 **predicate** set: two numeric and two date predicates, `AND`ed, with `count(*)` |
| `q6-revenue` | **TPC-H Q6 itself**: `sum(l_extendedprice * (1 - l_discount))` over a tighter predicate |

The last two are both "Q6", and they are different queries. `q6` is Q6's *filter*, and it is what
the repository measured for three increments. `q6-revenue` is Q6's *aggregate* — an arithmetic
expression, summed — and it is the query TPC-H actually asks. Both are published, so the cost of
the arithmetic is a **difference between two measured numbers** rather than an assertion.

### 2a. Resident — the data is already in memory

The like-for-like comparison: all three systems hold the data in memory and answer the query.

| query | **engine** | duckdb | polars | datafusion | |
|---|---|---|---|---|---|
| `scan` | **0.0 ms** | 2.0 ms | 0.2 ms | 1.0 ms | engine wins |
| `filter-numeric` | **3.5 ms** | 15.0 ms | 11.5 ms | 10.3 ms | engine wins |
| `filter-string` | **3.2 ms** | 33.0 ms | 39.1 ms | 17.0 ms | engine wins |
| `filter-range` | **7.3 ms** | 20.0 ms | 12.4 ms | 11.1 ms | engine wins |
| `q6` | **10.5 ms** | 45.0 ms | 71.6 ms | 24.3 ms | engine wins, by 4.3× |
| `q6-revenue` | **17.3 ms** | 49.0 ms | 74.0 ms | 63.6 ms | engine wins, by 2.8× |

**The engine wins all six, against a Rust peer on the same Arrow stack.** The `datafusion` column is
`DataFusion` 49.0.2 reading the same Parquet through Arrow 55.2.0, one thread, in the same harness.

**These figures moved, and this increment did not touch the resident query.** The resident path never
goes through the lazy scan — the scan that compacts is the *lazy* one — and spec 016's change is in
the **read** path, which a resident query does not use: the data is decoded before the clock starts.
What moved is the machine. The eager load was 844.6 ms in the last campaign and is 575.5 ms in this
one, and DuckDB's load was 1793.0 ms and is 1328.0 ms, so the drift is in both directions and in
both systems. The table's figures are published as they were measured, with the machine's drift in
them, and the change is attributed from the **back-to-back** measurement in §2b, not from comparing
two campaigns taken on different days.

`filter-range` was the loss, and it was not a filter problem. That query's stages were filter 1.4 ms,
**project 7.8 ms**, aggregate 2.2 ms: the projection was materialising a column that **nobody would ever
see**. The aggregate sums it and throws it away, and a plan *with* an aggregation ignores the projection,
because the aggregate result is the output. The engine now folds the column **where it lies**, over the
filter's selection, and the projection materialises nothing at all:

| | before | after |
|---|---|---|
| `filter-range` resident | 14.6 ms | **6.9 ms** |
| its **project** stage | 7.0 ms | **0.0 ms** |
| its aggregate stage | 2.4 ms | **1.9 ms** |

That is the whole of the loss, and it is gone. In this set the engine's resident `filter-range` is
**7.3 ms against Polars' 12.4 ms and DuckDB's 20.0 ms.** See
[ADR-0016](docs/adr/0016-the-aggregate-reads-in-place.md).

**The engine's query is 4.3× faster than `DuckDB`'s** (10.5 ms against 45.0 ms, resident) and 6.8×
faster than `Polars`'s — and 2.3× faster than `DataFusion`'s, which is a Rust engine on the same
Arrow stack, answering the same SQL, on the same file, at the same thread count. The lazy path does
not change this: it reads the file *during* the query, so it has no resident form and does not
compete in this table.

### 2b. Cold — read the Parquet file and answer in one go

The engine is measured **twice** here. The **eager** path decodes every column of the file before
the query starts. The **lazy** path reads only the columns the plan needs, with the plan's
predicates applied during the scan, so it has no resident form: its number is a cold number
by construction.

| query | **engine** (eager) | **engine** (lazy) | duckdb | polars | datafusion |
|---|---|---|---|---|---|
| `scan` | 575.5 ms | **0.1 ms** | 2.0 ms | 1.0 ms | 1.3 ms |
| `filter-numeric` | 590.4 ms | **5.0 ms** | 22.0 ms | 45.0 ms | 15.6 ms |
| `filter-string` | 566.3 ms | **9.6 ms** | 22.0 ms | 166.8 ms | 25.0 ms |
| `filter-range` | 575.1 ms | 16.5 ms | 32.0 ms | **16.4 ms** | 22.6 ms |
| `q6` | 564.3 ms | **15.0 ms** | 32.0 ms | 196.5 ms | 36.7 ms |
| `q6-revenue` | 578.2 ms | **62.0 ms** | 69.0 ms | 200.7 ms | 117.0 ms |

**The lazy path is 37.6× faster than the eager one on `q6`, and it is ahead of DuckDB on it** —
15.0 ms against 32.0 ms, where it was 2.6× behind. It beats Polars on every cold query except
`filter-range` — and on the real Q6 it beats Polars by 3.2×.

**It beats DuckDB on `q6-revenue` too**, by 1.11×, where it was 2% behind. Five of the six cold
queries are the engine's, and the sixth is Polars' by 0.1 ms.

**It also beats DuckDB on `filter-numeric`** — 5.0 ms against 22.0 ms, 4.4× — and on
`filter-string`, by 2.3×. Those are the first cold queries the engine wins against DuckDB on this
file, and they are published as what they are.

**And it beats the Rust peer on every cold query**, by 3.1× on `filter-numeric` and **1.9× on the
real Q6** — 62.0 ms against DataFusion's 117.0 ms, on the same file, with the same SQL, at the same
thread count, and with the answer cross-checked.

**The real Q6 is 62.0 ms against DuckDB's 69.0 ms — and the arithmetic is 0.85 ms of it.** §3h
takes the query apart as a ladder: the predicates alone are 21.31 ms, the materialised column adds
**36.69 ms**, and the aggregate over the 110,915 rows that survived the filter adds **0.85 ms**.
The cost of the real Q6 is the cost of **reading `l_extendedprice`**, which is the biggest column
in the file, and not the cost of computing with it.

That is the finding the increment produced, and it is the reason there is no vectorised
arithmetic kernel: the arithmetic was never the bottleneck. See
[ADR-0012](docs/adr/0012-arithmetic-expression.md).

**The one-thread table is not the whole picture, and §2e and §2f are the rest of it.** Every system
here is pinned to one thread, which is the like-for-like *single-threaded* comparison and is
unchanged since the first set of numbers in this file. But `DuckDB` uses every core by default, so
a user running `DuckDB` does not get 32.0 ms — they get 10.0 ms. The sweeps in §2e and §2f run the
engine and both incumbents at the same thread counts and show the whole curve.

### 2b-bis. The eager path got faster too, and it is measured

Spec 001 recorded the eager path's cold `q6` at **1921 ms**. In the measurement set that followed
it was **1181 ms** — 1.6× faster — and the cause was not the machine being quieter. It is a defect
that spec 002 fixed on the way to building something else. (The eager path's figure in the
current set is **564.3 ms**, and it moved again when spec 008 parallelised the decode — see the
load table in §2d and [§2g](#2g-the-load-sweep--where-the-engines-biggest-number-was).)

Both paths share one decode function. That function used to copy a dictionary column's distinct
values out of *every batch* to merge them, when the merge is a lookup and needs no copy. The lazy
path never paid it: it does not materialise the dictionary column at all — the pushed predicate is
evaluated on Arrow's array directly, and the plan reports `materialised columns: (none)` — so the
copy never happened there. The eager path pays it in full: it materialises all sixteen columns,
its reader hands the file over in 5,860 batches, and every one of them copied 2,500 distinct
strings. About 14.6 million string allocations, to build a dictionary of 2,500 entries.

Putting the copy back, deliberately, and re-measuring, gives the numbers rather than the story:

| | eager `q6` cold | lazy `q6` cold |
|---|---|---|
| with the per-batch copy | **1889.9 ms** | 119.0 ms |
| without it | **1181.1 ms** | 121.5 ms |

The eager path is 1.60× faster. The lazy path does not move — 119.0 against 121.5 ms is inside
its 2.6% spread — which is the control that makes the attribution credible: the fix helps the
path that copied and leaves the path that did not.

Both columns are from the measurement set that preceded the pushdown rewrite, and they are the
figures that set was made of. The eager path's current published figure is 564.3 ms and the
lazy path's is 15.0 ms. The lazy path moved because spec 003 rewrote the pushdown, and again when
spec 016 aligned the reader's batch size with the file's row groups; the eager path moved twice
more since — the dictionary fix above, and then spec 008's parallel decode, which is
[§2g](#2g-the-load-sweep--where-the-engines-biggest-number-was).

The perturbed run is committed as
[`bench-results/experiment-dictionary-copy.json`](bench-results/experiment-dictionary-copy.json),
and it is **not** one of the three reports the published table is derived from.

### 2c. The lazy scan, and what it reads

The lazy path is the change spec 002 made. It does three things:

1. **It resolves the plan against the file's schema**, before reading anything, so an unknown
   column or a type mismatch is an error before a single row is decoded.
2. **It reads only the columns the plan needs.** The reader is handed a projection over the file's
   root columns; the bytes of the others are never fetched from the file.
3. **It pushes the plan's predicates into the reader**, so the rows that fail them are dropped
   during the scan rather than after it.

For `q6` that is **two columns of sixteen**:

```
columns read: l_discount, l_shipdate
pushed down: l_discount >= 0.04 and l_discount <= 0.07,
             l_shipdate >= '1994-01-01' and l_shipdate < '1995-01-01'
```

Per the Parquet footer's own metadata, those two columns are 3.0 MiB and 9.1 MiB compressed
across the file's six row groups — **12.1 MiB of the file's 231.6 MiB**, and 2.9% of its raw
bytes. `l_comment` alone, which the eager path decodes and throws away, is 50% of the raw bytes.

**The gap against DuckDB is not pruning. It is threads.** This was published as a pruning gap
once, and that was wrong; here is DuckDB's own plan for the same query on the same file:

```
╭─ Table Scan ───────────────────────────────╮
│ Function: READ_PARQUET                      │
│ Filters: (l_discount >= 0.04) AND ...      │
│ Row Groups Scanned: 6 / 6                   │
│ 315,203 rows                               │
╰─────────────────────────────────────────────╯
Data Read: 12.3 MB
```

**6 / 6 row groups scanned, 12.3 MB read** — the same two columns, the same bytes the engine
reads. DuckDB prunes *nothing* here, because there is nothing to prune with: the file has no page
index. The generator writes `EnabledStatistics::Chunk`, so there are no per-page statistics, and
neither system can skip a page it has never been told about. The engine fetches every page of the
predicate's column because the `ArrowPredicate` path evaluates over the decoded batch — but so
does DuckDB, because there is no page index to select against.

What is left is throughput, and it decomposes cleanly:

| | engine | duckdb | ratio |
|---|---|---|---|
| **Reader speed**, same job: decode all 16 columns into memory | **575.5 ms** | 1328.0 ms | **2.31× — the engine is ahead** |
| **Architecture**: read 2 columns and push the predicate down | **15.0 ms** | 32.0 ms | **0.47× — the engine is ahead** |

**Both terms now favour the engine.** The reader-speed term was **1.58×** in DuckDB's favour when
ADR-0008 recorded it; the shared decode path and the dictionary fix closed it; spec 008's parallel
eager decode took it the other way, and the engine's full-file decode is now **2.3× faster** than
DuckDB's. The architecture term was the other way round — it was **2.6×** in DuckDB's favour until
spec 009, and the engine's lazy scan of two columns is now **2.1× faster** than DuckDB's.

That is what the decomposition in [ADR-0015](docs/adr/0015-the-engine-keeps-the-mask.md) found.
The architecture term was never about the architecture. It was about a **row-range list**: the
pushdown's mask was handed to the reader as a row filter, parquet-rs turned it into a list of
2,775,138 ranges for 2,178,861 surviving rows, and the reader applied that list one range at a
time. Reading one column through the list cost **50.0 ms** against **7.8 ms** without it. The
engine now keeps the mask — one bit per row — and applies it itself.

| | duckdb, one thread | duckdb, fourteen threads |
|---|---|---|
| `q6` cold | **32.0 ms** | **10.0 ms** |

**DuckDB gets 3.2× from fourteen cores on exactly this work**, and the engine was single-threaded
by design, in this increment, because the comparison pins both incumbents to one thread to make
the comparison like-for-like. That pinning was the reason for the gap, and it was a decision this
repository made on purpose.

**Spec 005 closed most of that gap.** The engine's read is now parallel over the file's row
groups, and it preserves the file's row order exactly, so the answer does not depend on the
scheduler. §2e is the measurement. The one-thread gap was 2.1×; at six workers it was **2.5×**.

**Spec 009 closed the rest of it.** The engine's lazy scan is now **15.0 ms** at one thread against
DuckDB's **32.0 ms**, and **4.0 ms** against DuckDB's **10.0 ms** at six workers. The engine is ahead at
every thread count in §2e.

The residue that is left is the engine's own plan output, and it is small: the pushdown costs
7.3 ms of the scan — measured on the set before this one, where the scan was 24.5 ms — and that
7.3 ms is the comparison over 12,000,000 rows — twice the
rows it used to be evaluated over, because the second predicate's column is no longer narrowed by
the first. That is the price of not building the range list, and it is paid in full view.

**The eager path's decode is now 2.3× faster than it was, and it still decodes too much.** 231.6
MiB in 0.58 s is about 402 MiB/s — the same work as the 275 MiB/s of the set before this one, which

where the other thread counts live.

**The subprocess wall clock is not the query.** It is the tool's own overhead, outside its load and
query timers: `DuckDB`'s command line client costs about 50 ms, and `Polars`' Python interpreter
plus the `polars` import about 105 ms, which is more than most of the queries in the table above.
Both are excluded from the query figures — they come from the tools' own timers — and both are
reported here.

against 8.0 ms) — against 7.6× and 3.5× in the set before this one. The gap narrows, because
DuckDB's parallel filter over the survivors scales better than the engine's.

**Every system's speedup rose, and the machine is the reason.** The engine gets 4.27× from
fourteen workers here, against 1.61× in the set before it; DuckDB's rises from 3.52× to 5.75× and
Polars' from 3.3× to 7.3×. **That is the machine, not the engine**: the increment before this one
changed the **read** path, and a resident query never uses it — the file is decoded before the
clock starts. What moved is how well the box could keep fourteen workers busy, and it moved for
every system at once. The *comparison* is what holds, and it is the comparison this table is for.

**The operators' worker count is not capped at six, and that is the difference from §2e.** The
read's parallelism is capped by the file's six row groups; the **operators'** is capped by the row
count, so at eight and fourteen threads the filter runs eight and fourteen workers. The table
records the workers that ran, because the requested count and the actual one now differ in a way
they did not before.

**The engine's own curve is monotone here, and the spread says why the old one was not.** On `q6`
the fourteen-thread row is 1.8 ms with a **1.7–2.1 ms** range, and the eight-thread row is 2.0 ms
with a 1.7–2.6 ms
range: the machine could give the fourteen workers a quiet run this time. The same is visible in
DuckDB's row — 9.0 ms at eight threads and 8.0 ms at fourteen — and in Polars' 10.9 ms and
9.5 ms. Every one of them is published rather than dropped, and the engine's `q6-revenue` row
shows the same shape: 4.0 ms at four threads, 3.5 ms at eight, 3.4 ms at fourteen, with spreads
of 3.8–4.3 ms, 3.4–4.6 ms and 3.3–4.1 ms. The medians are the figures, and the spread
is the evidence that the *curve* is the host's here.

**These figures are not the same as §2b's resident row, and the difference is the harness.** The
comparison harness re-reads the file inside every iteration, so each resident query runs after a
231 MiB decode has churned the allocator. The resident sweep loads the file once and then runs
the query against it. Both are published.

### 2g. The load sweep — where the engine's biggest number was

The **load** is the time to get the file into memory: the engine decodes every column into its own
chunk format, `DuckDB` into a temp table, `Polars` into a frame. It is the only measurement in
this file that is about the *file* rather than the *query*, and it was the engine's worst figure —
**1277.8 ms**, the largest number in the repository, and the one place the engine was behind both
incumbents.

So it is swept the same way as the other two: the engine and both incumbents load the same file at
the same thread counts, in the same harness.

| threads | engine's workers | **engine** (load) | duckdb (load) | polars (load) | datafusion (load) | engine vs duckdb |
|---|---|---|---|---|---|---|
| 1 | 1 | **576.8 ms** | 1275.0 ms | 1069.8 ms | 362.3 ms | **2.2× ahead** |
| 2 | 2 | 423.9 ms | 635.0 ms | 536.1 ms | 242.0 ms | 1.5× ahead |
| 4 | 4 | 312.2 ms | 423.0 ms | 372.5 ms | 128.5 ms | 1.4× ahead |
| 6 | 6 | **251.0 ms** | 239.0 ms | 193.5 ms | 127.7 ms | **0.95× — behind** |
| 8 | 6 | 246.0 ms | 245.0 ms | 200.2 ms | 76.0 ms | 1.00× level |
| 14 | 6 | 243.9 ms | 235.0 ms | 204.8 ms | 83.5 ms | 0.96× — behind |

Every figure is the median of three full sweeps of five timed iterations. The raw reports are
`bench-results/scaling-load-run{1,2,3}.json`, and `python3 scripts/medians.py` re-derives the table
from them.

**Every absolute figure in this table is smaller than the set it replaces, and the reason is the
host.** The engine's one-thread load was **842.3 ms** in the set before this one and is **576.8 ms**

The set before it was measured on a machine under another tenant's memory pressure — see
[The conditions](#the-conditions) — and every system moved by roughly that much, the other way.
The *ratios* are what this table is about, and they hold.

**The engine goes from 0.95× DuckDB to 2.2× DuckDB at one thread.** The load was the one place
the engine was behind, and at one thread — where the comparison is like-for-like — it is now the
one place it is furthest ahead of DuckDB.

**At six threads DuckDB is ahead, 239.0 ms against the engine's 251.0 ms, and the reason is the
file.** The read splits the file's
**row groups** across the workers, and this file has **six** — so six workers is the ceiling, and
the curve is flat from six threads on. `DuckDB` is not capped by the file and keeps using threads,
and it is ahead by 4–5% at six and fourteen threads, where the engine is behind; in the set before
this one the engine was 1.2× ahead at six. `Polars` is a little ahead of the engine at every count.
The `DataFusion` peer is **faster than
everybody** on this measurement, and it is the one system in the table that does not decode the
file into the engine's own chunk format at all — it reads the file where it lies.

**Most of the win was not the parallelism.** The eager path used the Parquet reader's default
batch size of 1,024 rows, and the per-batch cost scales with the number of columns — the eager
path reads all sixteen, so it rebuilt sixteen dictionary tables 5,860 times instead of 733. In a
controlled comparison — the same binary, the same process shape, one change at a time — fixing
that constant took the one-thread load from **1145.6 ms to 587.0 ms**, and the parallel decode
took it the rest of the way to **550.2 ms** — and the one-thread load is **576.8 ms** in this set,
on a machine that is no longer under another tenant's memory pressure. The full account is in
[ADR-0014](docs/adr/0014-parallel-eager-decode.md).

**And spec 016 gave this path the same rule the lazy path got.** The eager read had the same
defect — a batch size that divided no row group's row count — and it now derives its batch from
the file the same way. The load sweep above is the only published measurement of that change on
the eager path, and it is measured on the host's conditions, so it is published as measured.

## 3. What the engine's own stages say

The plan output splits the engine's work by stage. The two blocks in [§3b](#3b-the-query-that-no-longer-materialises-anything)
are the **median of three runs of each build**, measured back to back on this machine, so the two are
comparable rather than two runs of the same code on a busy afternoon.

For the Q6 predicate set, resident:

```
stage      rows in  rows out  elapsed
scan       6000000  6000000   0.0 ms
filter     6000000  315203    6.7 ms
project    315203   315203    0.0 ms
aggregate  315203   1         0.0 ms
```

The filter stage does four predicates over 6,000,000 rows. The numeric ones run through the SIMD
kernel at 8.7 G rows/s, which is 0.7 ms each. The two date predicates run through the dictionary
path — one comparison per distinct date, then a map through the indices.

**The kernel is no longer the bottleneck of this query.** That is the point of the project, and it
took two defects to get there: a mask accumulation that extracted two lanes to scalar registers
every two rows (ADR-0006), and a dictionary map that used a mispredicted branch to set a bit. A
single date predicate on its own — the `filter-string` query — now takes 2.4 ms in the filter
stage, against 16.5 ms before the branchless rewrite.

### 3c. The real Q6's stages, and what the arithmetic costs

The real Q6 has one more stage, and it is the one this increment added:

```
stage      rows in  rows out  elapsed
scan       6000000  407082    67.3 ms
filter     407082   110915    0.3 ms
project    110915   110915    0.9 ms
evaluate   110915   110915    0.2 ms
aggregate  110915   1         0.1 ms
```

**The `evaluate` stage is 0.2 ms of a 70 ms query — 0.3%.** That is the whole cost of the
arithmetic aggregate, and it is small for a reason that was a design decision rather than an
accident: the expression is evaluated over the **110,915 rows that survived the filter**, not
over the 6,000,000 rows of the file. SQL applies `WHERE` before the aggregate, and so does this.

The scan is 67.3 ms because the real Q6 reads `l_extendedprice`, which is the biggest column
in the file. **The cost of the real Q6 is the cost of reading a column, not the cost of
computing with it** — and that is why there is no vectorised arithmetic kernel in this
increment. See [ADR-0012](docs/adr/0012-arithmetic-expression.md).

**The `project` stage is 0.9 ms, and it is not fused away.** The aggregate reads
`l_extendedprice` and `l_discount` through an **expression**, and an expression is evaluated over
the survivors — so its operands have to be aligned with them, and they are gathered. The fusion
in §3b reaches a column that only a **plain** aggregate reads, and not one that an expression
reads.

### 3d. The same query, on six workers

The plan output reports the workers that ran, and the stages show what they did:

```
stage      rows in  rows out  elapsed

project    110915   110915    0.9 ms
evaluate   110915   110915    0.3 ms
aggregate  110915   1         0.2 ms
read threads: 1
operator workers: 6 filter, 6 projection
```

**The filter stage falls from 6.3 ms to 2.1 ms — 3.0× from six workers.** The projection falls
from 1.3 ms to 0.9 ms, and the two stages that do not parallelise — `evaluate` and `aggregate` —
are unchanged, because they are not parallelised.

**The `evaluate` and `aggregate` stages do not move, and they are not going to.** `evaluate` is
0.2 ms and `aggregate` is 0.1 ms; together they are 0.3 ms of a 3.1 ms query. Parallelising the
aggregate is forbidden — `SUM` is not associative, and the answer must not depend on the block
boundaries — and parallelising the evaluation would mean slicing the columns into blocks, a copy
per column, to save a fraction of a millisecond.

**The answer is the same bits.** `group [] -> [Float(5526985127.48064)]`, one thread and six, and
the CLI's end-to-end test checks it against DuckDB's answer on the real file.

### 3e. The scan's decomposition, and what the compaction was worth

The plan output reports the scan stage and the pushdown's cost inside it. It does **not** say how
much of the scan is Arrow's own decode and how much is the engine's own work — and that is the
question this increment had to answer before it could fix anything. The probe is in the tree, as
`crates/columnar-engine/examples/filter_range_scan_decomposition.rs`, and it takes the real file,
the real predicates and the real batches:

| | |
|---|---|
| **Arrow's own decode** of `l_quantity` and `l_discount`, with no filter and no conversion | **10.7 ms** |
| **the predicates**, over the whole column | **0.7–1.4 ms** |
| the filter and the copy, in the shape the engine used | **4.7 ms** |
| **the engine's own scan**, end to end | **16.1 ms** — before spec 016, in an earlier campaign; **15.32 ms** now, with the derived batch (§3j) |

**The first three rows are the decomposition and the batch size does not change them** — the same
rows are decoded and the same comparisons are made. The fourth row is end-to-end, and spec 016
moved it: the scan is **15.32 ms** on the same file with the derived batch, against **19.98 ms**
with the fixed one, in the same campaign. That is the fix, and it is in
[§3j](#3j-the-row-group-count-and-what-it-costs).

And the same work in three shapes, on the same file, in the same process:

| | |
|---|---|
| **A — filter the whole batch, then copy** (the shape in the tree) | **4.7 ms** |
| **B — filter only what is kept** | **3.3 ms** |
| **C — compact once, into the chunk** (the shape in the tree now) | **2.5 ms** |

**Two things fall out of that, and they are the whole of this increment.**

**The predicates are not the gap.** 0.7–1.4 ms of a 16 ms scan is 4–9%. The README said the next
thing to do was "narrowing the predicates in the engine's own domain", and that was **wrong** —
there was nothing there to recover. It is corrected in the README rather than quietly dropped.

**Arrow's decode is 10.7 ms and it is the floor.** That is the cost of the bytes, and no
arrangement of the engine's own code goes below it. The engine's own work on top of the decode was
5.4 ms, and that was what was available to win.

And the defect is in the middle of that 5.4 ms: the scan filtered the **whole batch** with Arrow's
`filter_record_batch` and then copied the survivors **a second time** out of the filtered batch. So
it copied the column the query does not materialise — the predicate's column, which was about to be
thrown away — and then copied the survivors again. **Shape C is half of shape A**, and the scan's
stage went from 18.5 ms to 15.1 ms.

**The batch size was measured too, because a constant that depends on the shape of the work has to
be.** The lazy path's batch size has been measured three times now, because the *shape* of the work
has changed three times since the first measurement: the pushdown became the engine's own kernel,
the mask stopped going to the reader as a list of row ranges, and the scan stopped filtering the
whole batch and copying the survivors twice. A constant measured for a shape that no longer exists
is not a measured constant for the shape that does.

**And after spec 016 the batch size is not a constant at all.** The reader's batch size is now
**derived from the file** — the largest divisor of the row groups' row count that fits under a
limit — so what is measured now is the **limit**, and the batch follows from the file. The probe
sweeps the limit over the two shapes the lazy path serves, prints the batch each limit derives for
the published file, and A/Bs the batch the tree used before against the batch it derives now, with
the order alternating on every round so that a drifting machine cannot bias the result. The raw

### 3f. The scan's read is the Parquet decode, and owning it is not worth it

The cold path's one remaining loss is `filter-range`, by 1.1 ms, and the scan that holds it is 15.7 ms of the 17.5 ms
query. The obvious next move is the one every columnar engine makes eventually: **stop going through Arrow and read
the Parquet file into the engine's own column format.** Arrow's reader is a thin wrapper over the parquet crate's own
reader — it decodes a column chunk into a buffer and *moves* that buffer into an Arrow array — so the engine could use
the parquet crate directly, apply its own mask to the decoded values, and write the survivors straight into its own
column.

It was prototyped as a full read path and measured, and the measurement says **no**. The probe is in the tree, as
`crates/columnar-engine/examples/own_decode_probe.rs`, and it measures four things on the same file, in the same
process, warm, each the median of five runs:

| | |
|---|---|
| **A** | the parquet crate's own decode of the two columns, into plain Rust buffers | **10.30 ms** |
| **B** | Arrow's decode of the same two columns | **9.86 ms** |
| **C** | A, plus the engine's predicate over the decoded buffer, plus the compaction of the survivors into the engine's own column | **15.73 ms** |
| **D** | the engine's own scan, as it is today | **15.74 ms** |

**C is D.** The shape without Arrow is equal to the engine's scan, to a tenth of a millisecond. And **A is B**:
Arrow's reader is not slower than the parquet crate's raw reader, because it *is* the parquet crate's reader with an
array wrapper on top — and the wrapper is worth **0.3 ms** on a 15.7 ms scan.

**So Arrow is not the cost, and the engine keeps Arrow.** The rewrite is refused, and the receipt is published, because
a measurement that says "no" is worth more than the increment it refuses: a future contributor does not have to spend
a week discovering that the Arrow layer is worth 0.3 ms. See
[ADR-0018](docs/adr/0018-the-scan-reads-the-parquet-decode.md).

**The same measurement pointed at where the decode's time is.** The file's columns are **dictionary-encoded** — per
the Parquet footer's own metadata, one row group of 1,000,000 rows:

| column | encodings | uncompressed |
|---|---|---|
| `l_quantity` | PLAIN, RLE, **RLE_DICTIONARY** | 1,667,405 bytes — **1.67 bytes a row** |
| `l_discount` | PLAIN, RLE, **RLE_DICTIONARY** | 503,674 bytes — **0.50 bytes a row** |

A `float64` column at 1.67 bytes a row is not storing floats: it is storing a **dictionary of a few dozen values** and
a million **RLE indices** into it, and the decode is the work of **expanding** those indices back into a million
values.

**And the engine throws most of that expansion away.** The predicate column is expanded into six million floats,
compared row by row, and then dropped — because the query does not materialise it. The engine already knows how to
compare a column without expanding it: the dictionary path compares **one distinct value at a time**, which is why
the predicates cost 1.4 ms rather than 14.

That is the next increment — [spec 012](specs/012-the-scan-does-not-expand-the-predicates-column/spec.md) — and it is
a **hypothesis**, measured before anything is built, the way this one was.

### 3g. The expansion of the RLE indices, and why it is not the decode's cost

The hypothesis §3f ends on was specific: **the predicate's column is expanded into six million values, compared, and
thrown away, and the engine could compare the dictionary instead and apply the mask to the indices.** Spec 012's T3
is the test of it, and the test came out **no**.

The probe is in the tree, as `crates/columnar-engine/examples/rle_expansion_probe.rs`. It measures eleven things on
the same file, in the same process, warm, each the median of five runs, over **three campaigns**; the raw reports are
in `bench-results/rle-expansion-run{1,2,3}.json` and the table below is derived from them by
`python3 scripts/medians.py`.

| | | median (min–max) |
|---|---|---|
| **P** | the parquet crate's own decode of the column | **7.20 ms** (6.90–7.61) |
| **A** | Arrow's decode of the column — what the engine's reader does | **4.13 ms** (3.85–4.29) |
| **PLAIN** | the decode of the **same column written without a dictionary**, through Arrow | **4.69 ms** (4.62–4.72) |
| **V** | the probe's decode: the indices *and* the gather | **6.39 ms** (6.24–6.52) |
| **I** | the probe's decode of the indices **only**: no gather, no values | **5.09 ms** (4.96–5.23) |
| **G** | **the expansion**: the reader's fresh buffers, and the gather | **1.79 ms** (1.78–1.81) |
| **G1** | the reader's fresh buffers, and their zeroing | **0.21 ms** (0.21–0.22) |
| **G2** | the gather alone | **1.60 ms** (1.59–1.62) |
| **M** | **the mask the hypothesis would have to build** from the indices | **1.73 ms** (1.72–1.84) |
| **C** | the hypothesis's shape, end to end | **8.02 ms** (7.74–8.06) |
| **S1** | the engine's scan of the predicate's column | **5.22 ms** (5.10–5.41) |
| | of which the predicate itself | 1.31 ms |
| **S2** | the whole query | **43.84 ms** (43.08–44.84) |

**The expansion is real, and it is not the decode's cost.** `l_discount` is a `float64` column stored as **eleven
distinct values** and a million RLE indices into them — four bits a row, 502,051 bytes of indices for a row group of
1,000,000 rows. The expansion is **1.79 ms** of the engine's **3.91 ms** decode of that column, so **46% of it** — and
that decode is **8.9% of the query**, which makes the expansion **4.1% of the 43.84 ms query**.

**The decode's cost is the bytes.** The same column, written without a dictionary, holds 48,025,815 bytes against the
dictionary's 3,012,834, and Arrow decodes it in **4.69 ms** against the dictionary's **4.13 ms**. The dictionary
encoding wins by 0.56 ms *despite* paying the 1.79 ms expansion: the expansion costs less than the forty-five megabytes
it saves, which is the whole reason the file is dictionary-encoded.

**The replacement is not cheaper than what it replaces.** The mask is still one bit per row, and the row's bit is the
predicate's answer for the row's index — so the engine has to build it per row, out of the indices. That is **M**:
**1.73 ms**, against the **1.31 ms** the vectorised predicate costs today. There is no cheap "test a bit at a variable
index" instruction, so the mask from the indices is a scalar loop, and it costs **0.42 ms more** than the comparison it
would replace.

**And the indices cannot be had for free.** The parquet crate does not expose them: the expansion is inside
`DictDecoder::get`, its `RowFilter` and `ArrowPredicate` evaluate on the *decoded* batch, `DictIndexDecoder` is in a
private module, and `RleDecoder` is `pub(crate)`. So the engine would have to **own the Parquet reading** — this
spec's own non-goal, and ADR-0018's refusal. The price of owning it is measurable: the probe's own decoder of the
format, checked bit-for-bit against the crate's, is **0.81 ms faster** than the crate's, and that cancels most of the
increment.

| | |
|---|---|
| the expansion, saved | 1.79 ms |
| the mask from the indices, minus the predicate it replaces | −0.42 ms |
| **the net, with the crate's own RLE decoder** | **1.37 ms** |
| the probe's RLE decoder, against the crate's | −0.81 ms |
| **the net, with the decoder the probe actually wrote** | **0.56 ms** |

**So the increment is refused**, and the receipt is published, the way §3f's was: **0.56 ms on a 43.84 ms query** for
a rewrite of the read path and a new implementation of the Parquet format's index encoding. The hypothesis was not
wrong about the file — the column is dictionary-encoded, and the decode does expand six million indices. It was wrong
about the size of the prize. See [ADR-0020](docs/adr/0020-the-expansion-is-not-the-decode-s-cost.md).

One fact an implementation would have to respect, which the probe found the hard way: **every row group has its own
dictionary**, built in the order the values were first seen in that chunk, so two row groups hold the same eleven
values in a different order. The probe's first attempt at the mask was wrong by 3,671 rows because of it.

### 3h. The materialised column, and what it is made of

§3g took the **predicate's** column apart. The query's time is not the predicate's column: on the real Q6 the engine
spends a few milliseconds on the column it filters on and the rest on the column it **materialises** —
`l_extendedprice`, the column the revenue is computed from. Spec 014 takes that column apart with the same
instrument, and then runs the **real Q6** through the engine's own lazy path.

The probe is in the tree, as `crates/columnar-engine/examples/materialised_column_probe.rs`. It measures the same

the figures.

**The materialised column is most of the query, and it is bytes.** 36.69 ms of the 59.78 ms query is the

materialisation of it is 36.69 ms, so **the engine is 2.43 ms from the floor the Arrow stack sets** — 7.1% above
it. There is nothing in the engine's read path to fix.

**And it is not an expansion of dictionary indices.** §3g's expansion was 1.79 ms of the predicate's column, and
here the expansion is 1.11 ms of a column whose pages are mostly plain: the file's writer starts a dictionary for
every column and falls back to plain when the dictionary page reaches its size limit — one megabyte by default.
`l_extendedprice` has 131,411 distinct values per row group, so its dictionary page would be 1.05 MB and the
writer abandoned it part-way through the first pages of each row group.

**The counterfactual says that was the right call.** The same column, written with a dictionary and a dictionary
page big enough to keep it:

| | the file's column | the counterfactual | |
|---|---|---|---|
| on disk | **36,451,424 bytes** | 47,499,582 bytes | **30% bigger** |
| Arrow's decode | **34.26 ms** | 37.03 ms | **8% slower** |

The dictionary is a **loss** for this column. **And the opposite is true of the two predicate columns**: `l_discount`
written plain is 22.08 ms against the dictionary's 4.62 ms — 4.8× slower — and 11,644,361 bytes against
3,023,401; `l_quantity` written plain is 34.64 ms against 6.09 ms, 5.7× slower, and 26,980,250 bytes against
9,904,661. So "should this column be dictionary-encoded" is **not a rule, it is a measurement**: the dictionary
pays for a column with a few thousand distinct values and loses for one with a hundred thousand.

One thing the file does carry for nothing: the writer's fallback leaves the dictionary page in the file —
**6,313,096 bytes** over the six row groups, **2.6%** of the file — that no reader reads. It costs disk and
nothing else, and it is a fact about the *generator*, not about the engine.

**ADR-0018's non-goal stands, and this is the other side of it.** Owning the Parquet reading would buy the
engine the difference between Arrow's decode and the parquet crate's: **2.50 ms** on the materialised column and
**2.98 ms** on `l_discount` — Arrow is already faster than the crate on both. It would also cost the Parquet
format's RLE decoder, which has to match the crate's bit for bit, and the crate does not expose its RLE. The
measurement does not reopen that question: **the materialised column is bytes, and the bytes are what they are.**

**And the instrument had to be fixed before it could measure anything.** At four bits — the predicate's column —
the probe's decoder is competitive with the crate's. At **thirteen bits** it was not: the bit-at-a-time path made
the probe's decode of `l_quantity` **39.55 ms** against the crate's **7.92 ms** — in the set that found the bug —
so the probe was measuring itself. The decoder now reads a group's eight values as one 128-bit word, and the
probe's decode of `l_quantity` is **9.24 ms** against the crate's **8.46 ms**. The probe's decoder is still
verified against the parquet crate's, bit for bit, over every value of every row group, before it measures
anything.

See [ADR-0021](docs/adr/0021-the-materialised-column-and-a-rust-peer.md).

### 3i. The curve over the size of the data

§2e and §2f sweep the **thread count** and §2g sweeps the **load**. This is the third axis: the query and the
thread count are held fixed and the **size of the data** moves. It is the axis a reader asks about when they want
to know what a query costs *per row*, and the table carries that figure beside the timings.

The real Q6 is measured at **three dataset sizes** — 6, 12 and 24 million rows — generated by this repository's
own generator from the pinned seed 24001, with the scale factor, the row count and the byte count recorded in each
manifest. The generator is **byte-deterministic**: scale factor one at seed 24001 is `data/lineitem.parquet`, with
the same SHA-256. Every system is measured at every size, in the same harness, on the same file, with the thread
count pinned to one. The raw reports are in `bench-results/curve-run{1,2,3}.json` and the table below is derived
from them by `python3 scripts/medians.py`.

| rows | sf | MiB | **engine** | engine scan | engine ops | duckdb | polars | datafusion | **ms/Mrow** |
|---|---|---|---|---|---|---|---|---|---|
| 6,000,000 | 1 | 231.6 | **57.7 ms** | 56.8 ms | 1.6 ms | 69.0 ms | 197.4 ms | 114.6 ms | **9.6** |
| 12,000,000 | 2 | 465.4 | **114.3 ms** | 111.5 ms | 2.9 ms | 139.0 ms | 390.1 ms | 223.5 ms | **9.5** |
| 24,000,000 | 4 | 936.2 | **232.2 ms** | 226.3 ms | 5.9 ms | 268.0 ms | 774.7 ms | 451.1 ms | **9.7** |

The stage columns are the last run of each campaign and the total is the median over five runs, so at the smallest
size the two disagree by 1% — that is the run-to-run spread on a busy machine, not a disagreement about the
work.

**The cost per row is flat, and that is the finding.** 9.6, 9.5 and 9.7 ms a million rows: the engine's cost
does **not** amortise as the file grows. It is exactly what §3h predicts — the query's cost is **bytes**, and
bytes cost what they cost — and it is the answer to the question a reader asking about the size axis has. A
curve that fell would have said the fixed costs dominate; this one does not fall.

**The engine is ahead of every incumbent at every size.** DuckDB by 1.20×, 1.22× and 1.15×; Polars by 3.4×, 3.4×
and 3.3×; and the Rust peer by 2.0×, 2.0× and 1.9×. The margin over DuckDB is **about the same at every
size** — 1.15× to 1.22× — and DuckDB's scan does get relatively better on the bigger files than on the small
one, and it is worth saying that plainly rather than quoting only the sizes where the engine is ahead.

**The scan is the query at every size**, and the operators grow from 1.6 ms to 5.9 ms as the rows that survive the
filter grow — and they stay at **2–3%** of it. The arithmetic aggregate is not the bottleneck at any size, which is
what §3c found at one size and this confirms at three.

**One thing the curve found that is not a timing: the engine's default memory budget refuses the real Q6 at 24
million rows.** The estimate is about 16 bytes a row — the materialised column, the mask and the machinery — so
24 million rows need roughly **391 MiB** against the **256 MiB** default, and the query is rejected before a row is
read. The budget is a **policy knob**, not a limit on the engine: below it, it changes nothing at all, and the
curve is measured at **1024 MiB** so that the largest size runs at all. The number is in the report, because a
curve that says which budget it was measured under is a curve a reader can check.

### 3j. The row-group count, and what it costs

§2e says the engine's parallelism is capped by the **file's** row-group count, and until this
increment that sentence was an inference from a single file with six row groups. The row-group
size is now a **knob**: `columnar-cli dataset --row-group-rows N` writes the file with N rows per
row group, the manifest records both N and the number of row groups written, and the benchmark
report carries the row-group count so that a sweep says how many row groups the file it swept
had. The default is unchanged — a million rows, six row groups — so every figure published before
this increment is still reproducible by the command that made it.

Three files were generated from the same seed, the same six million rows and the same schema, and
they differ in one thing: **six, twelve and twenty-four row groups**. All three were swept and
probed in **one session**, interleaved, so that a difference between them is a difference between
the files rather than a difference between two times on a shared machine.

**The cap is `min(threads, row_groups)`, and it is now measured rather than inferred:**

| threads | 6 groups: workers | 6 groups: engine | 12 groups: workers | 12 groups: engine | 24 groups: workers | 24 groups: engine |
|---|---|---|---|---|---|---|
| 1 | 1 | 15.4 ms | 1 | 15.7 ms | 1 | 16.4 ms |
| 2 | 2 | 8.2 ms | 2 | 8.8 ms | 2 | 8.8 ms |
| 4 | 4 | 6.1 ms | 4 | 4.9 ms | 4 | 5.4 ms |
| 6 | 6 | 4.0 ms | 6 | 4.2 ms | 6 | 4.4 ms |
| 8 | **6** | 4.7 ms | **8** | 4.1 ms | **8** | 4.6 ms |
| 14 | **6** | 4.1 ms | **12** | 4.3 ms | **14** | 4.8 ms |

The workers column is `min(threads, row_groups)` at every point of every sweep, and nothing else
explains it: the same file, the same query, the same machine, the same harness, and the worker
count follows the row-group count exactly.

**And the file's row-group count no longer costs the engine anything.** The engine's one-thread
figure across the three files is **15.4, 15.7 and 16.4 ms** — within 7% of each other, where before
the fix it was 19.7, 24.8 and 34.6 ms, and the file with the most row groups was 76% slower than
the file with the fewest.

**The same thing, measured back to back.** The per-row-group cost probe puts the engine's scan at
two batch sizes in one session: the fixed 65,536 rows the tree used, and the batch the tree derives
now. Same build, same file, same process:

| the engine's scan, one thread | 6 groups | 12 groups | 24 groups |
|---|---|---|---|
| the fixed 65,536 rows — the defect | 19.98 ms | 24.60 ms | 34.00 ms |
| **the derived 125,000 rows — the fix** | **15.32 ms** | **15.13 ms** | **15.51 ms** |

**The defect's cost is 4.7, 9.5 and 18.5 ms**, and the fix's cost is **flat within 2.6%**. That is
the whole of the finding, in one table: the same measurement, the same session, the same machine,
one row of it broken and one row of it fixed. The raw reports are
`bench-results/row-group-cost-{6,12,24}-run{1,2,3}.json`, and `python3 scripts/medians.py` derives
the table from them.

**And the ladder says what the mechanism is.** The same probe runs the engine's own scan at eight
reader batch sizes, on each of the three files:

| the reader's batch | 6 groups | 12 groups | 24 groups | ms a row group |
|---|---|---|---|---|
| 12,500 | 22.73 ms | 22.73 ms | 23.34 ms | 0.034 |
| 25,000 | 18.46 ms | 18.81 ms | 19.50 ms | 0.058 |
| 31,250 | 17.85 ms | 17.88 ms | 19.00 ms | 0.064 |
| 50,000 | 15.96 ms | 16.56 ms | 17.19 ms | 0.068 |
| 62,500 | 15.85 ms | 16.12 ms | 16.23 ms | 0.021 |
| **65,536** — divides none of them | **19.98 ms** | **24.60 ms** | **34.00 ms** | **0.779** |
| **125,000** — the fix | **15.32 ms** | **15.13 ms** | **15.51 ms** | **0.010** |
| 250,000 | 14.69 ms | 15.20 ms | 15.77 ms | 0.060 |

**Seven of the eight batch sizes divide the row group's row count, and every one of them costs
0.01–0.07 ms a row group. The eighth — 65,536, which divides none of 1,000,000, 500,000 or 250,000
— costs 0.78.** The mechanism is a property of the *shape* of the number and not of its size: a
batch size that divides the row group's row count ends the row group on a batch boundary, and one
that does not leaves a **partial** batch at the end of every row group.

**And the attribution says which column pays it.** The crate's read of each column, on its own, at
the fixed batch — and the engine's own scan, at the derived batch, beside it:

| | 6 groups | 12 groups | 24 groups | ms a row group |
|---|---|---|---|---|
| the crate's read of `l_shipdate` | 10.39 ms | 15.16 ms | 25.32 ms | **0.830** |
| the crate's read of `l_discount` | 3.99 ms | 3.86 ms | 4.79 ms | 0.044 |
| the crate's read of `l_extendedprice` | 3.48 ms | 3.51 ms | 3.71 ms | 0.013 |
| **the engine's own scan, the derived batch** | **15.39 ms** | **15.00 ms** | **15.79 ms** | **0.023** |

**`l_shipdate` alone carries it.** The other two columns' reads are flat across the three files —
0.044 and 0.013 ms a row group — and the engine's own scan, at the derived batch, is flat at 0.023.
Which of `l_shipdate`'s properties makes it the one that pays — its string dictionary, its page
count, or its size — **is not separated by this measurement**, and it is written down as the next
question rather than guessed at.

**The incumbents are the control, and they did not move with the row-group count**, which is what
says the file did not change and the engine's read did:

| at one thread | 6 groups | 12 groups | 24 groups |
|---|---|---|---|
| **the engine** | **15.4 ms** | **15.7 ms** | **16.4 ms** |
| duckdb | 33.0 ms | 30.0 ms | 31.0 ms |
| polars | 193.6 ms | 189.5 ms | 191.7 ms |
| datafusion | 37.4 ms | 39.1 ms | 40.5 ms |

**What the fix was.** The parquet crate's reader reads a row group at a time, and the reader's
**batch size** decides where a batch ends. When the batch size does not divide a row group's row
count, the row group's last batch is **partial** — and **a partial batch costs 0.78 ms** on this
shape. The engine's batch size was 65,536 rows, which divides none of 1,000,000, 500,000 and
250,000, so the engine paid that once per row group, and the incumbents did not pay it at all. The
reader's batch size is now **the largest divisor of the row groups' row count that fits under the
limit**, so no row group ends with a partial batch. The full account is in
[ADR-0023](docs/adr/0023-the-per-row-group-cost.md).

**The encoding changed too, and it is a small effect.** The writer's one-megabyte dictionary page
limit is **per row group**, so a smaller row group carries a smaller dictionary, and the
high-cardinality column's dictionary fits where it did not before. The same probe that took the
materialised column apart in §3h, run on all three files:

| `l_extendedprice` | 6 groups | 12 groups | 24 groups |
|---|---|---|---|
| written | **plain** | **plain** | **plain** |
| pages | 42 dictionary, 258 plain | 84 dictionary, 216 plain | 168 dictionary, 144 plain |
| dictionary-page bytes — **read by nobody** | 6,313,096 | 12,627,464 | **25,259,152** |
| plain-data bytes | 41,646,592 | 35,290,624 | 22,578,688 |
| Arrow's decode | 34.26 ms | 34.47 ms | 35.32 ms |
| **the materialised column's share of the query** | **36.69 ms** | **35.16 ms** | **36.45 ms** |

The smaller row groups really do make the materialised column *more* dictionary-encoded — 168
dictionary pages against 42 — and they really do leave **four times as many dead dictionary pages**
in the file, 25.3 MB that no reader reads. But the column's decode moves by **3%** and **its share
of the query by none at all** — 36.69 ms against 36.45 ms — so the encoding is a small effect in
this set. The predicates' cost moves by **11%**, and what is left of *that* is the dictionary work
per row group, not the partial batch.

**And the query itself, through the engine's own lazy path, as the ladder §3h uses:**

| the real Q6 | 6 groups | 12 groups | 24 groups |
|---|---|---|---|
| **Q0** the predicates alone | **21.31 ms** | **21.58 ms** | **23.75 ms** |
| **Q4** the whole query | **59.78 ms** | **58.74 ms** | **63.07 ms** |
| of which the scan stage | 57.67 ms | 56.22 ms | 61.87 ms |

**What is left is not the partial batch, and this measurement says so.** The two-predicate shape —
the one the sweep and the cost probe run — is flat across the three files: **15.4, 15.7 and 16.4
ms**, and **15.32, 15.13 and 15.51 ms** in the probe's own back-to-back ladder. The real Q6's
**three**-predicate shape still rises by about **0.14 ms a row group**, and the two shapes differ by
exactly one thing: the third predicate's column, `l_quantity`, which is dictionary-encoded with
4,901 values a row group. So what remains is **dictionary work per row group** — the crate
building that dictionary, and the engine comparing its distinct values — and not the partial batch.

**Which of the two it is is not separated by this measurement**, and it is written down as the next
spec's question rather than guessed at: the crate's per-row-group dictionary build, or the
engine's per-row-group comparison of the dictionary's distinct values. The incumbents' three-predicate
figures on these files were not measured, so this file does not claim that they do not pay it.

**The knob works, the published claim is confirmed, and the price is now the encoding and the
dictionary.** The row-group count is a knob; the parallelism above six workers was real and is
measured; the engine's read no longer pays for the row groups it reads; and the remaining per-row-group
cost is 0.14 ms of dictionary work, on a query that reads three predicate columns.

**The engine's speedup at fourteen threads is 3.74×, 3.63× and 3.39×** — and it no longer *rises*
with the row-group count, which is the point. It used to rise because the engine's **serial** cost
grew with the row groups: more row groups meant more of the defect, and a bigger serial part means
a bigger ratio. Now the serial part is flat, so the speedup is set by the parallelism alone — and
the cap above it is still `min(threads, row_groups)`.

**The per-row-group cost is gone.** On the probe's own back-to-back ladder it is **0.78 ms** with
the fixed batch and **0.01 ms** with the derived one — a 99% reduction. Spec 015 published the
same defect as **0.83 ms a row group**, measured on the sweep's one-thread Q6 across the three
files (19.7 → 34.6 ms); the sweep's one-thread figures are now **15.4, 15.7 and 16.4 ms**, flat,
so there is no per-row-group cost left to measure there either.

**The best figure is the six-row-group file's again.** It was 4.0 ms there in the set before this
one, against 4.3 and 5.4, and it is 4.1 ms there now, against 4.3 on the twelve-group file and 4.8
on the twenty-four-group one. The absolute figures are this set's, and this set was measured on a
host that was busy but no longer thrashing — see
[The conditions](#the-conditions) — but the *one-thread* figures, which are the ones the defect
was in, are flat: **15.4, 15.7 and 16.4 ms**.

**That last part was a defect, and spec 016 fixed it.** A defect gets its own spec: the engine's
read path had a per-row-group cost that the Parquet readers the incumbents use do not have, and
spec 016 measured the mechanism and removed it. See
[ADR-0023](docs/adr/0023-the-per-row-group-cost.md).

The global aggregate is the one worth calling out from the first increment: the module
documentation promised that `COUNT(*)` was an in-place fast path that reads no column, and it did
read no column — but it still allocated a key vector and did a hash-map lookup for every one of
the six million rows, in order to arrive at the same answer every time. The fix is a separate
path for the global case, where there is exactly one group and there never was a key.

The three rows about the reader, the conversion and the mask are from spec 002's increment, and
they are the same kind of defect: work done per batch, per predicate or per dictionary, where the
shape of the problem does not need it. The reader decodes a column once per projection mask that
mentions it, so two predicates on one column means two decodes — they are now pushed as one. The
conversion was copying the dictionary's distinct values out of every batch to merge them, when the
merge is a lookup and needs no copy. And the mask was being built through a builder whose
per-element capacity check costs more than the comparison it was carrying, when the mask is a bit
vector and can be written a word at a time.

The figure for that one, on the published median of three runs, was **84.4 ms** in the set that
followed the pushdown rewrite and **82.4 ms** in the set after it; in this set it is **15.0 ms**,
because the machine is no longer under memory pressure.

One of the three turned out to be worth more than the increment that found it. The dictionary copy
was invisible on the path spec 002 was building, because the lazy path never materialises the
column — and it was worth 1.60× to the path it was not building, because the eager path
materialises all sixteen columns across 5,860 batches. See [§2b-bis](#2b-bis-the-eager-path-got-faster-too-and-it-is-measured).

The pushdown row is the same kind of defect, found the same way: **a total that was never
attributed**. The scan's 121.5 ms was never split into the reader's decode and the comparison,
and the comparison turned out to be 42.9 ms of it — the larger half of the single-column scans,
and 6.4× slower than the engine's own filter on the same work. A total is not an explanation,
and the plan output now says which half is which.

**The last row is spec 010's, and it is the same kind of defect again: work done for a shape the
problem does not have.** The projection gathered 2,178,861 survivors into a column of their own —
17.4 MB of values — and the aggregate summed that column and threw it away, because a plan with
an aggregation ignores the projection. The global aggregate has one group and never needs its
values aligned with anything, so the copy was never needed. It cost **7.8 ms of a 14.6 ms query**,
and it is the whole of the one query the engine used to lose. See
[ADR-0016](docs/adr/0016-the-aggregate-reads-in-place.md).

**The last three rows are spec 008's, and they are the same kind of mistake again** — this time
about *constants* and about *how work is combined* rather than about work done per batch. The
batch size was inherited rather than measured. The merge grew with the square of the number of
parts. And the merge treated a NULL row's placeholder index as a live reference. The first was
worth 1.95× on its own, the second 90 ms at six parts, and the third changed no answer but did
change the bytes. See [ADR-0014](docs/adr/0014-parallel-eager-decode.md).

**And the last row is spec 016's, and it is the same kind of mistake for the third time: a constant
where the file's shape belonged.** Spec 008 measured a batch size and found one that was too
small; spec 016 found that the *right* answer was not a number at all but the file's own row-group
divisor — 65,536 was a constant that happened to divide no row group in any of the three files. The
cost was invisible in the shape the tree measured in, because that file's row group happened to be
friendly, and it was worth **0.83 ms a row group** on the files that were not. The engine's own
one-thread Q6 is now flat across the three files, where it was 76% apart. See
[ADR-0023](docs/adr/0023-the-per-row-group-cost.md).

## 5a. The performance gate

The constitution requires two gates — no statistically significant regression against a stored
baseline, and absolute budgets met — and until spec 004 neither existed. They do now, and they
are worth describing because of what they found.

`just perf-gate` measures the kernel, 32 independent blocks of 5 timed passes each, and compares
the samples against `bench-results/kernel-baseline.json` with a **Mann-Whitney U test**: the
exact permutation distribution for small samples, the normal approximation with tie and
continuity corrections for large ones. It is one-sided, in the direction "the current sample is
slower".

**The first version was statistically correct and useless.** Five consecutive runs against an
unchanged baseline produced:

| flavor | runs reporting a regression | the difference |
|---|---|---|
| `cpp-auto` | 5 of 5 | 1.3% – 2.3% slower |
| `cpp-simd` | 4 of 5 | 1.7% – 3.9% slower |
| `scalar` | 4 of 5 | 0.9% – 1.2% slower |
| `rust-simd` | 0 of 5 | — |

**Thirteen false positives in twenty checks, on code that had not changed.** The test was not
wrong: the machine's throughput drifts by a percent or two between one moment and the next, and
a test with 32 samples on each side detects that drift as significant every time.

So a regression now has to be **both** statistically significant **and** practically significant,
and the practical threshold is set from that measurement: **5%**, above the observed drift of
0.9%–3.9%. With it, five consecutive runs on unchanged code produce **zero** failures, and the
differences that remain are reported as *within the noise* rather than hidden.

The gate has four answers — no regression, within the noise, regression, and **inconclusive** —
and the last one is not a pass. It says the gate could not tell, which is more useful than a pass
that was decided by a threshold nobody examined.

**And the gate was green while this campaign ran.** It measured `cpp-simd` at **8.628 G rows/s**
against a stored baseline of **8.306 G**, and `scalar` at **3.532 G** against **3.469 G** — above
the baseline in both cases, where the set this campaign replaced ran with every flavour **46–53%
slower** than that same baseline. The baselines are the medians of the stored samples in
`bench-results/kernel-baseline.json`, and the gate's own readings for this campaign are in
[The conditions](#the-conditions). The gate is what says the machine was not thrashing while this
file's figures were taken, and it is why they are about 40% faster than the set they replace.

## 6. Reproducing this

```bash
just dataset       # 6,000,000 rows, deterministic, about 2.8 seconds
just bench         # the kernel A/B -> bench-results/kernel.json
just compare       # DuckDB and Polars  -> bench-results/compare.json

just check-x86     # compile the x86-64 half of the kernel, from this ARM64 Mac
just verify-avx2   # run the AVX2 path under Rosetta 2 and check it against the oracle

python3 scripts/medians.py   # the published table, derived from the committed reports

just perf-gate      # the performance gate: measure, and compare against the baseline
just perf-baseline  # rewrite the baseline from a fresh measurement
```

`just compare` needs `DuckDB` on `PATH` or in `tools/bin/`, and the `polars` Python package
installed. Both versions are recorded in the report.

**The row-group files of §3j are made by the same generator with one flag different:**

```bash
just dataset                       # the published file: six row groups
just dataset-row-groups 500000     # twelve row groups
just dataset-row-groups 250000     # twenty-four row groups

just sweep data="data/lineitem-rg250k.parquet" query="q6" threads="1,2,4,6,8,14" \
    iterations="3" mode="cold" out="bench-results/scaling-rg24-run1.json"
just probe data="data/lineitem-rg250k.parquet" out="bench-results/row-groups-24-run1.json"
```

**And the two instruments spec 016 added**, one per file, three campaigns each:

```bash
just probe-cost       data="data/lineitem.parquet" \
    out="bench-results/row-group-cost-6-run1.json"
just probe-batch-size data="data/lineitem.parquet" \
    out="bench-results/batch-size-run1.json"
```

`probe-cost` is the per-row-group cost probe: the crate's own read of each column, the engine's
scan, the page shape of every row group, and the ladder of reader batch sizes. `probe-batch-size`
sweeps the reader's batch **limit** over the two shapes the lazy path serves and A/Bs the batch
the tree used against the batch it derives now. The `row-group-cost-*` reports are the source of
the ladder and the attribution in [§3j](#3j-the-row-group-count-and-what-it-costs), and the
`batch-size-*` reports are the source of the two-shape table in
[§3e](#3e-the-scans-decomposition-and-what-the-compaction-was-worth).

Three campaigns of each, interleaved, and then `python3 scripts/medians.py` derives both tables.
The Polars driver needs an interpreter with `polars` in it: set `PYTHON_BIN` if `python3` is not
the one that has it.

The comparison harness measures the load and the query separately, takes the **median** of the
timed runs, and **cross-checks every answer against the engine's own**. The `SUM` over 555,594
rows differs in the last bits between systems — floating-point addition is not associative and
the engines sum in different orders — so the check uses a relative tolerance rather than exact
equality.

To publish a table, run `just compare` at least three times, keep the reports, and derive the
medians with `scripts/medians.py`. The three reports behind the table in §2 are committed as
`bench-results/compare-run1.json`, `compare-run2.json` and `compare-run3.json`.

## 7. How to read this file

The framing rule for this project is **"kernel X on query Y"**, never "this database versus
DuckDB". A number here is a statement about *one operation on one query on one machine*, and it
is only meaningful next to its conditions.

So: the comparison kernel on the Q6 predicate set is 1.47× faster than the compiler's own
vectorisation of the same loop, and 2.48× faster than a genuinely scalar reference, on an M4 Max
with NEON, single-threaded, over 20 million rows. The engine's filter on the Q6 predicate set
takes 6.7 ms. The engine's lazy scan of the same file, reading the two columns Q6 needs and
pushing the predicates down into the scan, takes **15.4 ms** at one thread — against **33.0 ms**
for DuckDB and **193.6 ms** for Polars — and at six workers it takes **4.0 ms** against DuckDB's
10.0 ms. The lazy path is **2.1× faster than DuckDB** at one thread and 12.6× faster than
Polars, and the reason it was not faster before is measured and named: the pushdown's mask was
handed to the reader as a row filter, and a row filter is a list of 2,775,138 row ranges for
2,178,861 surviving rows, applied one range at a time. The engine keeps the mask now, and the
scan that uses it copies each surviving row **once**.

**And the last defect this file records is the per-row-group cost.** The engine's reader used a
fixed batch of 65,536 rows, and that number divides none of the three files' row-group sizes — so
every row group ended on a **partial** batch, and a partial batch costs 0.78 ms. The engine paid
a per-row-group cost that DuckDB, Polars and the DataFusion peer did not pay, and the file with
the most parallelism was the slowest one. The batch size is derived from the file now, and the
engine's one-thread figure is flat across the three files — **15.4, 15.7 and 16.4 ms**, where it
was 19.7, 24.8 and 34.6. See [§3j](#3j-the-row-group-count-and-what-it-costs).

And the eager read — the file → queryable load, which was the largest number in the repository —
is now **576.8 ms** against DuckDB's **1275.0 ms** on the same file at the same thread count, and
251.0 ms at six workers. It is the one measurement in this file that is about the *file* rather
than the *query*, and it is swept like the other two. See [§2g](#2g-the-load-sweep--where-the-engines-biggest-number-was).
**Every absolute figure in this paragraph is this set's**, and this set was measured on a host
that was busy but no longer thrashing — see [The conditions](#the-conditions). The ratios are
what the file claims, and they hold.
