# PERF.md — the measured numbers, and the conditions they were measured under

Every number in this file was produced by `just bench` and `just compare` on the machine
described below, and the raw JSON is in `bench-results/`. Nothing here is estimated, extrapolated
or carried over from another machine.

**The tables below are derived, not typed.** The engine's comparison table is the median of
three full `just compare` runs, and the derivation is a checked-in script:

```bash
python3 scripts/medians.py
```

All three raw reports are committed, so the published figures can be re-derived by a reader
without re-running a benchmark. See [`bench-results/README.md`](bench-results/README.md).

the lazy `q6` cold figure 85.1, 83.3 and 88.2 ms — a 5.8% spread, which is comfortable. The
*eager* figures spread 1260 to 1288 ms, because the eager path reads 231 MiB and every stall in
that read lands in the number. DuckDB's spread furthest of all, 32.0 ms on `q6` in every run but

allocator and the page cache. The sweep measures the lazy path on its own. Both numbers are
published, because the difference between them is the harness's shape and not the engine's speed
— and a reader who compared the two would otherwise have to wonder.

**Every figure in this file is from this set**, and the comparison is like-for-like within it:
every system was measured on the same file, on the same machine, in the same three runs.

## 1. The comparison kernel

**What is measured:** one pass over a column of `f64` values, comparing every row against a
threshold and writing a bit mask. 20,000,000 rows, column `l_discount`, operator `>=`,
threshold `0.04`. Median of 8 runs.

### Two baselines, not one

| flavor | what it is | rows/sec | ns/row | vs scalar | vs cpp-auto | matches |
|---|---|---|---|---|---|---|
| `scalar` | the C++ reference compiled with `-fno-vectorize` | 3.48 G | 0.288 | 1.00× | 0.60× | 12,726,115 |
| `cpp-auto` | **the same source**, compiled with ordinary flags | 5.75 G | 0.174 | 1.67× | 1.00× | 12,726,115 |
| `cpp-simd` | the hand-written NEON kernel, over the C ABI | 8.73 G | 0.115 | 2.50× | **1.50×** | 12,726,115 |
| `rust-simd` | the Rust `std::arch` intrinsics kernel, no FFI | 8.72 G | 0.115 | 2.51× | 1.51× | 12,726,115 |

**The spread, because a benchmark that only publishes its best numbers is not a benchmark.** Over
the 8 runs: `scalar` 2.80–3.51 G, `cpp-auto` 5.45–5.90 G, `cpp-simd` 7.56–8.83 G, `rust-simd`
4.77–8.93 G. This machine is not isolated, and single runs occasionally drop — the `rust-simd`
low of 4.77 G is one such run, in which every flavor was slower than its own median. The median
is the number to quote; the range is the noise floor.

**These numbers reproduce.** An earlier session measured the same kernel on the same machine and
got `scalar` 3.51 G, `cpp-auto` 5.87 G, `cpp-simd` 8.81 G, `rust-simd` 8.77 G — within 2% of the
medians above, and with the same `2.51×` and `1.50×` ratios. Two independent 8-run sets agreeing
to 2% is a stronger claim than either set alone.

Every flavor agrees on the match count, and the differential tests compare the **masks bit for
bit**, not just the counts.

### What the two ratios mean

- **`scalar → cpp-simd` is 2.50×.** This is how much vectorisation is worth, measured against a
  reference that really is scalar. It is checked against the disassembly: the `-fno-vectorize`
  object contains **zero** vectorised loop instructions, and the ordinary object contains ~300.
- **`cpp-auto → cpp-simd` is 1.50×.** This is the one that decides whether the hand-written kernel
  earns its complexity: it beats what clang produces from the same loop by half.

The first version of this table published one ratio, against a baseline that clang had
auto-vectorised. It was measuring two vectorised implementations. See
[ADR-0006](docs/adr/0006-auto-vectorised-baseline.md).

### The FFI seam

`cpp-simd` crosses a C ABI; `rust-simd` does not. They are within **0.2%** of each other — 8.73 G
against 8.72 G — against a run-to-run spread of a few percent. The seam is free. See
[ADR-0003](docs/adr/0003-cpp-ffi-seam.md).

### AVX2 correctness (verified on an ARM64 Mac)

**This is not a performance claim.** It is the answer to "this machine has no AVX2", and the answer
turned out to matter more than expected.

The project has two SIMD paths: NEON, measured above on this machine, and AVX2, for x86-64. The
development hardware is an ARM64 MacBook, so the AVX2 half could not be *timed* here — and, when
somebody finally tried to cross-build it, it turned out it could not be *compiled* either. The
AVX2 Rust intrinsics path had never been built by anyone. It had two type errors in it (`u32`
accumulated into a `u64` mask), and it had been sitting in the tree, unchecked, for the entire life
of the project. See [ADR-0009](docs/adr/0009-avx2-without-x86-hardware.md).

The fix has two halves.

**Compilation** is now gated. `just check-x86` cross-compiles the workspace for
`x86_64-apple-darwin` on this machine, and CI runs the same check. The AVX2 path cannot rot
unnoticed again.

**Correctness** is now testable here, because Rosetta 2 executes AVX2 instructions correctly on
Apple Silicon while reporting *no* AVX2 in CPUID — the host is an ARM64 chip, so the feature bits
say so. The kernel's runtime probe therefore correctly concludes that there is no AVX2 path and
never enters it. `COLUMNAR_FORCE_SIMD=avx2` overrides the probe, which is what `just verify-avx2`
does:

```
$ just verify-avx2

-- without the override --
    forced        : auto
    simd_kind     : none
    avx2 rows     : 0
    matches oracle: true

-- with COLUMNAR_FORCE_SIMD=avx2 --
    forced        : avx2
    simd_kind     : avx2
    avx2 rows     : 1024
    matches oracle: true

RESULT: PASSED -- 3 test binaries green under Rosetta 2 with AVX2 forced.
```

The `avx2 rows` counter is the load-bearing part. A dispatch that *reports* the AVX2 path is not
proof that the path's instructions ran; the counter moves only if they did, and the mask it
produced is compared against the oracle's bit for bit. So the claim is narrow and specific: **the
AVX2 path — both the C++ FFI path and the Rust intrinsics path — compiles, executes, and produces
masks identical to the oracle's, on an ARM64 Mac.**

**What this does not establish: any AVX2 performance number.** Under Rosetta the instructions are
emulated, so a timing taken there measures the translator, not hardware. The benchmark harness
therefore *refuses to measure* while the override is in force — `just bench` exits with an
explanation rather than producing a number that means something other than what it appears to mean.
AVX2 timings require an x86-64 machine with AVX2, and are published only from one. See
[Not measured](#not-measured).

## 2. The engine, against DuckDB and Polars

Six queries, each measured twice: **resident** (the data is already in memory) and **cold** (the
Parquet file is read as part of the measurement). Both incumbents answer the same question in the
same mode, and every answer is cross-checked against the engine's.

The queries:

| name | what it is |
|---|---|
| `scan` | `SELECT count(*)` over every row |
| `filter-numeric` | one numeric predicate, `l_discount >= 0.04` |
| `filter-string` | one predicate on the dictionary-encoded `l_shipdate` |
| `filter-range` | two numeric predicates `AND`ed, and a `SUM(l_quantity)` |
| `q6` | the TPC-H Q6 **predicate** set: two numeric and two date predicates, `AND`ed, with `count(*)` |
| `q6-revenue` | **TPC-H Q6 itself**: `sum(l_extendedprice * (1 - l_discount))` over a tighter predicate |

The last two are both "Q6", and they are different queries. `q6` is Q6's *filter*, and it is what
the repository measured for three increments. `q6-revenue` is Q6's *aggregate* — an arithmetic
expression, summed — and it is the query TPC-H actually asks. Both are published, so the cost of
the arithmetic is a **difference between two measured numbers** rather than an assertion.

### 2a. Resident — the data is already in memory

The like-for-like comparison: all three systems hold the data in memory and answer the query.

| query | **engine** | duckdb | polars | |
|---|---|---|---|---|
| `scan` | **0.0 ms** | 1.0 ms | 0.2 ms | engine wins |
| `filter-numeric` | **2.8 ms** | 12.0 ms | 10.2 ms | engine wins |
| `filter-string` | **3.6 ms** | 32.0 ms | 36.9 ms | engine wins |
| `filter-range` | 15.1 ms | 19.0 ms | **11.4 ms** | polars wins, engine 1.33× slower |
| `q6` | **9.8 ms** | 44.0 ms | 67.9 ms | engine wins |
| `q6-revenue` | **15.2 ms** | 46.0 ms | 70.5 ms | engine wins, by 3.0× |

**The engine wins five of the six, and loses one.**

The loss is `filter-range`, and it is not a filter problem. That query's stages are: filter
1.6 ms, project 7.3 ms, aggregate 2.2 ms. The engine materialises the projected column and then
sums it; `Polars` streams the sum over the selection without materialising anything. The pinned
optimization order says "late materialization", but the projection and the aggregate are two
separate stages rather than one fused operator, and the gap is the materialisation.

**The engine's query is 4.5× faster than `DuckDB`'s** (9.8 ms against 44.0 ms, resident) and 6.9×
faster than `Polars`'s. The lazy path does not change this: it reads the file *during* the query,
so it has no resident form and does not compete in this table.

### 2b. Cold — read the Parquet file and answer in one go

The engine is measured **twice** here. The **eager** path decodes every column of the file before
the query starts. The **lazy** path reads only the columns the plan needs, with the plan's
predicates pushed into the Parquet reader, so it has no resident form: its number is a cold number
by construction.

| query | **engine** (eager) | **engine** (lazy) | duckdb | polars |
|---|---|---|---|---|
| `scan` | 1277.8 ms | **0.1 ms** | 2.0 ms | 1.1 ms |
| `filter-numeric` | 1278.3 ms | **18.5 ms** | 22.0 ms | 43.6 ms |
| `filter-string` | 1281.6 ms | 30.1 ms | **21.0 ms** | 160.1 ms |
| `filter-range` | 1292.9 ms | 94.1 ms | 31.0 ms | **15.0 ms** |
| `q6` | 1289.7 ms | 83.2 ms | **31.0 ms** | 187.8 ms |
| `q6-revenue` | 1287.4 ms | 143.5 ms | **67.0 ms** | 195.1 ms |

**The lazy path is 15.5× faster than the eager one on `q6`, and it turns a 41.6× gap against DuckDB
into a 2.7× one.** It beats Polars on every cold query except `filter-range` — and on the real
Q6 it beats Polars by 1.4× while DuckDB is 2.1× ahead.

**It also beats DuckDB on `filter-numeric`** — 18.5 ms against 22.0 ms — which is the first cold
query the engine wins against DuckDB on this file. It is a narrow win, inside the noise of
DuckDB's own spread (21.0 to 22.0 ms across the three runs), and it is published as what it is:
a tie the engine takes, on one query, by a margin smaller than the machine's noise.

**The real Q6 is 143.5 ms against DuckDB's 67.0 ms — and the arithmetic is 0.2 ms of it.** The
engine's own plan output says so: the scan is 140.2 ms, the filter 0.2 ms, the projection 0.8 ms,
the **evaluate** stage 0.2 ms and the aggregate 0.1 ms. The arithmetic aggregate costs *a
seventh of a millisecond* — 0.14% of the query — because it is evaluated over the 110,915 rows
that survived the filter and not over the 6,000,000 rows of the file. The cost of the real Q6 is
the cost of **reading `l_extendedprice`**, which is the biggest column in the file, and not the
cost of computing with it.

That is the finding the increment produced, and it is the reason there is no vectorised
arithmetic kernel: the arithmetic was never the bottleneck. See
[ADR-0012](docs/adr/0012-arithmetic-expression.md).

**The one-thread table is not the whole picture, and §2e and §2f are the rest of it.** Every system
here is pinned to one thread, which is the like-for-like *single-threaded* comparison and is
unchanged since the first set of numbers in this file. But `DuckDB` uses every core by default, so
a user running `DuckDB` does not get 32.0 ms — they get 10.0 ms. The sweeps in §2e and §2f run the
engine and both incumbents at the same thread counts and show the whole curve.

**The `scan` row deserves its own note.** `SELECT count(*)` needs no columns at all, so the lazy
path reads no column — it answers from the row count in the Parquet footer, in 0.1 ms. That is
faster than DuckDB's 2.0 ms and Polars' 1.0 ms, on the same file. It is also the narrowest
possible win, and it is in the table because the table is the table: a query that reads no data
should be fast, and here it is.

The two engines' answers are identical, row for row — the comparison harness refuses to report if
they are not — and so are the answers of all three systems, cross-checked at a relative tolerance
of 1e-9.

**These tables were re-measured under the parallel operators' code, and the numbers moved by about
a percent.** The previous set had `q6` lazy at **85.1 ms** and this one has **83.2 ms**; the
previous `q6-revenue` lazy was **144.7 ms** and this one is **143.5 ms**; the previous eager load
was **1265.2 ms** and this one is **1277.8 ms**. The incumbents moved by the same amount — DuckDB's
`q6` cold was **32.0 ms** and is **31.0 ms** — so the movement is the machine, not the code. **The
one-thread path is unchanged by this increment**: at one thread the filter and the projection run
the serial code, and the serial code is the code that was there before.

Both sets are published here rather than the second one quietly replacing the first, because the
difference is the machine's and a reader who compares this file against the last commit's should
be able to see that. The raw reports behind this table are
`bench-results/compare-run{1,2,3}.json`, re-measured under this commit.

### 2b-bis. The eager path got faster too, and it is measured

Spec 001 recorded the eager path's cold `q6` at **1921 ms**. In the measurement set that followed
it was **1181 ms** — 1.6× faster — and the cause was not the machine being quieter. It is a defect
that spec 002 fixed on the way to building something else. (The eager path's figure in the
current set is **1277.8 ms**; that is the machine, not the code — see the load table in §2d.)

Both paths share one decode function. That function used to copy a dictionary column's distinct
values out of *every batch* to merge them, when the merge is a lookup and needs no copy. The lazy
path never paid it: it does not materialise the dictionary column at all — the pushed predicate is
evaluated on Arrow's array directly, and the plan reports `materialised columns: (none)` — so the
copy never happened there. The eager path pays it in full: it materialises all sixteen columns,
its reader hands the file over in 5,860 batches, and every one of them copied 2,500 distinct
strings. About 14.6 million string allocations, to build a dictionary of 2,500 entries.

Putting the copy back, deliberately, and re-measuring, gives the numbers rather than the story:

| | eager `q6` cold | lazy `q6` cold |
|---|---|---|
| with the per-batch copy | **1889.9 ms** | 119.0 ms |
| without it | **1181.1 ms** | 121.5 ms |

The eager path is 1.60× faster. The lazy path does not move — 119.0 against 121.5 ms is inside
its 2.6% spread — which is the control that makes the attribution credible: the fix helps the
path that copied and leaves the path that did not.

Both columns are from the measurement set that preceded the pushdown rewrite, and they are the
figures that set was made of. The eager path's current published figure is 1277.8 ms and the
lazy path's is 83.2 ms; the eager path moved by nothing more than the machine's noise, and the
lazy path moved because spec 003 rewrote the pushdown.

The perturbed run is committed as
[`bench-results/experiment-dictionary-copy.json`](bench-results/experiment-dictionary-copy.json),
and it is **not** one of the three reports the published table is derived from.

### 2c. The lazy scan, and what it reads

The lazy path is the change spec 002 made. It does three things:

1. **It resolves the plan against the file's schema**, before reading anything, so an unknown
   column or a type mismatch is an error before a single row is decoded.
2. **It reads only the columns the plan needs.** The reader is handed a projection over the file's
   root columns; the bytes of the others are never fetched from the file.
3. **It pushes the plan's predicates into the reader**, so the rows that fail them are dropped
   during the scan rather than after it.

For `q6` that is **two columns of sixteen**:

```
columns read: l_discount, l_shipdate
pushed down: l_discount >= 0.04 and l_discount <= 0.07,
             l_shipdate >= '1994-01-01' and l_shipdate < '1995-01-01'
```

Per the Parquet footer's own metadata, those two columns are 3.0 MiB and 9.1 MiB compressed
across the file's six row groups — **12.1 MiB of the file's 231.6 MiB**, and 2.9% of its raw
bytes. `l_comment` alone, which the eager path decodes and throws away, is 50% of the raw bytes.

**The gap against DuckDB is not pruning. It is threads.** This was published as a pruning gap
once, and that was wrong; here is DuckDB's own plan for the same query on the same file:

```
╭─ Table Scan ───────────────────────────────╮
│ Function: READ_PARQUET                      │
│ Filters: (l_discount >= 0.04) AND ...      │
│ Row Groups Scanned: 6 / 6                   │
│ 315,203 rows                               │
╰─────────────────────────────────────────────╯
Data Read: 12.3 MB
```

**6 / 6 row groups scanned, 12.3 MB read** — the same two columns, the same bytes the engine
reads. DuckDB prunes *nothing* here, because there is nothing to prune with: the file has no page
index. The generator writes `EnabledStatistics::Chunk`, so there are no per-page statistics, and
neither system can skip a page it has never been told about. The engine fetches every page of the
predicate's column because the `ArrowPredicate` path evaluates over the decoded batch — but so
does DuckDB, because there is no page index to select against.

What is left is throughput, and it decomposes cleanly:

| | engine | duckdb | ratio |
|---|---|---|---|
| **Reader speed**, same job: decode all 16 columns into memory | **1265.2 ms** | 1228.0 ms | **1.03×** — DuckDB is ahead |
| **Architecture**: read 2 columns and push the predicate down | 85.1 ms | 32.0 ms | 2.7× |

The reader-speed term that ADR-0008 recorded as **1.58×** is **gone** — the shared decode path and
the dictionary fix closed it, and the engine's full-file decode is now level with DuckDB's rather
than half of it. The whole of the remaining 2.6× is the architecture term, and the architecture
term was mostly this:

| | duckdb, one thread | duckdb, fourteen threads |
|---|---|---|
| `q6` cold | **32.0 ms** | **10.0 ms** |

**DuckDB gets 3.2× from fourteen cores on exactly this work**, and the engine was single-threaded
by design, in this increment, because the comparison pins both incumbents to one thread to make
the comparison like-for-like. That pinning was the reason for the gap, and it was a decision this
repository made on purpose.

**Spec 005 closed most of that gap.** The engine's read is now parallel over the file's row
groups, and it preserves the file's row order exactly, so the answer does not depend on the
scheduler. §2e is the measurement. The one-thread gap was 2.7×; at six workers it is **1.6×**.

The residue that is left is the engine's own plan output, and spec 003 shrank it: the pushdown
was costing 42.9 ms of the scan, and now costs 6.1 ms.

### 2d. Where the cold time goes

| system | load (file → queryable) | subprocess wall clock |
|---|---|---|
| **engine** (eager, `Dataset::read_parquet`) | **1277.8 ms** | — (a resident process) |
| **engine** (lazy, `ParquetSource::open`) | **0.1 ms** | — (a resident process) |
| duckdb (`CREATE TEMP TABLE ... AS SELECT *`) | 1218.0 ms | 20.2 ms |
| polars (`pl.read_parquet`) | 1015.5 ms | 92.3 ms |

Several things are worth separating here.

**The lazy path's "load" is the footer.** 0.1 ms: the file's metadata, and nothing else. The data
is read during the query, which is why the lazy path has no resident form.

**The eager path's decode is slow, and it decodes too much.** 231.6 MiB in 1.28 s is about
181 MiB/s. That is the `arrow-rs` Parquet reader going through every column of every row group and
materialising all sixteen columns into the engine's own chunk format, eagerly, whether the query
needs them or not.

**The incumbents are pinned to one thread in the headline table.** `Polars` reads the file in
1027 ms single-threaded and in about 184 ms with all fourteen cores. That 5.6× is the price of
comparing a one-thread engine against a one-thread engine. It is the right price for the
*single-threaded* comparison, but it belongs in the reader's column, not the query's — and §2e is
where the other thread counts live.

**The subprocess wall clock is not the query.** `DuckDB`'s command line client starts in about
20 ms; `Polars`' Python interpreter plus the `polars` import takes about 90 ms, which is more
than most of the queries in the table above. Both are excluded from the query figures — they come
from the tools' own timers — and both are reported here.

### 2e. The thread-count sweep

The headline table in §2b pins every system to **one thread**, because that is the like-for-like
*single-threaded* comparison and it is the claim that has been in this file since the first set of
numbers. It is not the only table, because a one-thread table on its own is a misleading picture
of what a user sees: `DuckDB` uses every core by default, so a user running `DuckDB` gets
10.0 ms on `q6` cold, not 32.0 ms.

So the same file is swept. **The engine and both incumbents run at the same thread count at every
point**, on the same machine, in the same harness, and the answers are cross-checked at every
point — a sweep of systems computing different answers would be a sweep of nothing.

| threads | engine's workers | **engine** (lazy) | engine's scan stage | engine's operators | duckdb | polars |
|---|---|---|---|---|---|---|
| 1 | 1 | 81.1 ms | 81.1 ms | 0.0 ms | 32.0 ms | 188.8 ms |
| 2 | 2 | 42.8 ms | 42.8 ms | 0.0 ms | 21.0 ms | 100.3 ms |
| 4 | 4 | 29.7 ms | 29.7 ms | 0.0 ms | 14.0 ms | 67.9 ms |
| 6 | 6 | **16.2 ms** | 16.2 ms | 0.0 ms | **10.0 ms** | 37.5 ms |
| 8 | 6 | 16.0 ms | 16.0 ms | 0.0 ms | 10.0 ms | 37.4 ms |
| 14 | 6 | 15.9 ms | 15.9 ms | 0.0 ms | 10.0 ms | 37.4 ms |

Every figure is the median of three full sweeps, each of which takes the median of five timed
iterations. The raw reports are `bench-results/scaling-run{1,2,3}.json`, and
`python3 scripts/medians.py` re-derives this table from them.

**The engine gets 5.0× from six workers, against DuckDB's 3.2×.** The gap on `q6` cold narrows
from **2.5× at one thread to 1.6× at six**. The engine's curve is steeper than DuckDB's because
the parallel part is a larger fraction of its work: the engine's query is almost entirely *scan*,
while DuckDB's is a scan plus a parallel filter over 315,203 surviving rows.

**The engine's parallelism is capped by the file, not by the machine.** The read splits the file's
**row groups** across the workers, and this file has **six** of them — so six workers is the most
that can run, and the curve is flat from six threads on. The report says so explicitly: it
records the thread count *asked for* and the workers that *ran*, side by side. A file written with
larger row groups would go further, and that is a property of the file rather than of the engine.

**The operators' share of this table is 0.0 ms, and that is not a defect.** The `q6` predicate set
is **fully pushed down** into the reader, so the engine's own filter has nothing left to do — the
operators are in the scan stage. The query where they are not pushed down is `q6-revenue`, below,
and where they are the *whole* of the work is [§2f](#2f-the-resident-sweep-where-the-operators-are-the-measurement).

**The rows come back in the file's order, whatever the thread count.** `SUM` is not associative,
so a parallel read that ordered its rows by *completion* would make the answer depend on the
scheduler. The parallel read is bit-identical to the single-threaded one, and that is checked
rather than asserted — see [ADR-0011](docs/adr/0011-parallel-decode.md).

**The one-thread row in this table (81.1 ms) is not the one-thread row in §2b, and the difference is
the harness, not the engine.** The comparison harness measures the *eager* path first and the
*lazy* path second for each query, so the lazy measurement runs after a 231 MiB decode has churned
the allocator and the page cache. The sweep measures the lazy path on its own. Both are published;
a reader comparing them would otherwise have to wonder which is right.

### The same sweep, on the real Q6

The real Q6 reads `l_extendedprice` — the biggest column in the file — so its scan is heavier
than `q6`'s, and the sweep is worth publishing for it separately.

| threads | engine's workers | **engine** (lazy) | engine's scan stage | engine's operators | duckdb | polars |
|---|---|---|---|---|---|---|
| 1 | 1 | 142.3 ms | 140.9 ms | 1.3 ms | 69.0 ms | 194.5 ms |
| 2 | 2 | 75.0 ms | 73.7 ms | 1.2 ms | 39.0 ms | 105.4 ms |
| 4 | 4 | 52.6 ms | 51.3 ms | 1.2 ms | 27.0 ms | 69.6 ms |
| 6 | 6 | **30.4 ms** | 29.2 ms | 1.2 ms | **18.0 ms** | 41.5 ms |
| 8 | 6 | 31.2 ms | 29.6 ms | 1.4 ms | 18.0 ms | 40.3 ms |
| 14 | 6 | 31.2 ms | 29.0 ms | 1.8 ms | 18.0 ms | 40.2 ms |

**The engine gets 4.7× from six workers, against DuckDB's 3.8×**, and the gap narrows from
**2.1× at one thread to 1.7× at six**. The shape is the same as `q6`'s and for the same reason:
the engine parallelises the scan, and its query is almost entirely scan.

**The six-thread row has a wide spread: 30.4 ms is the median of 29.5, 30.1 and 37.6.** One run
was slow — the machine is shared and something else was running — and it is published rather than
dropped. It does not change the conclusion: the engine is still 1.7× behind DuckDB at six threads
and the conclusion is about the *median*, not about the fastest run.

**The arithmetic is not in any of these numbers.** The scan stage is 140.9 ms of the 142.3 ms
one-thread figure, and the evaluate stage — the arithmetic — is **0.2 ms**. The engine's number
is the cost of reading a column, and the arithmetic over the rows that survived the filter is
free.

**The operators' column is the whole story of this increment, and it is nearly flat.** The
operators are 1.3 ms of a 142.3 ms cold query — **0.9%** — because the reader pushed two of the
five predicates down and returned 407,082 rows, and the engine's filter only had to apply the
predicate on `l_discount`, which the expression also reads and which therefore could not be
pushed down. The operators' parallelism has almost nothing to work with *in the cold path*, and
the table says so rather than leaving a reader to assume otherwise. The path where they are the
query is [§2f](#2f-the-resident-sweep-where-the-operators-are-the-measurement).

### 2f. The resident sweep, where the operators are the measurement

The cold sweep measures the *read* and the operators together, and the read is 99% of it. That is
the right measurement for a user waiting on a command line, and the wrong one for the question
"how fast is the query engine".

So the same sweep is run again in **resident** mode: the file is loaded once, outside the timed
region, and the query is timed on its own. The incumbents are measured the same way, at the same
thread count, in the same harness — the symmetry the constitution requires.

**`q6`, resident:**

|---|---|---|---|---|---|
| 1 | 1 | 6.6 ms | 6.5 ms | 43.0 ms | 67.7 ms |
| 2 | 2 | 3.9 ms | 3.8 ms | 24.0 ms | 35.2 ms |
| 4 | 4 | 2.5 ms | 2.5 ms | 13.0 ms | 17.9 ms |
| 6 | 6 | **2.0 ms** | 2.0 ms | **10.0 ms** | 12.5 ms |
| 8 | 8 | 1.9 ms | 1.9 ms | 8.0 ms | 10.1 ms |
| 14 | 14 | 1.8 ms | 1.8 ms | 7.0 ms | 8.9 ms |

| threads | engine's workers | **engine** (resident) | engine's operators | duckdb | polars |
|---|---|---|---|---|---|
| 1 | 1 | 8.9 ms | 8.9 ms | 44.0 ms | 69.8 ms |
| 2 | 2 | 5.4 ms | 5.4 ms | 26.0 ms | 37.1 ms |

`bench-results/scaling-resident-run{1,2,3}.json` and
`bench-results/scaling-resident-revenue-run{1,2,3}.json`, and `python3 scripts/medians.py`
re-derives both tables from them.

**The engine gets 3.6× from fourteen workers on `q6` resident, against DuckDB's 6.1×.** The engine
is **6.5× faster than DuckDB** at one thread and **3.9× faster** at fourteen — the gap narrows,
because DuckDB's parallel filter over the survivors scales better than the engine's, but the
engine is ahead at every thread count measured.

**The operators' worker count is not capped at six, and that is the difference from §2e.** The
read's parallelism is capped by the file's six row groups; the **operators'** is capped by the row
count, so at eight and fourteen threads the filter runs eight and fourteen workers. The table
records the workers that ran, because the requested count and the actual one now differ in a way
they did not before.

**The `q6-revenue` row at fourteen threads is slower than at eight (3.4 ms against 3.2 ms), and
the spread says why: 3.4 is the median of 3.4, 3.4 and 4.2.** The machine is shared, the
fourteen-thread point is the one most likely to meet another process, and a median that moves
backwards is published rather than smoothed. The engine's resident `q6` — which has four
predicates over the same rows — does not show it: 1.9 ms at eight and 1.8 ms at fourteen.

**These figures are not the same as §2b's resident row, and the difference is the harness.** The
comparison harness re-reads the file inside every iteration, so each resident query runs after a
231 MiB decode has churned the allocator. The resident sweep loads the file once and then runs
the query against it. Both are published.

## 3. What the engine's own stages say

The plan output splits the engine's work by stage. For the Q6 predicate set, resident:

```
stage      rows in  rows out  elapsed
scan       6000000  6000000   0.0 ms
filter     6000000  315203    6.7 ms
project    315203   315203    0.0 ms
aggregate  315203   1         0.0 ms
```

The filter stage does four predicates over 6,000,000 rows. The numeric ones run through the SIMD
kernel at 8.7 G rows/s, which is 0.7 ms each. The two date predicates run through the dictionary
path — one comparison per distinct date, then a map through the indices.

**The kernel is no longer the bottleneck of this query.** That is the point of the project, and it
took two defects to get there: a mask accumulation that extracted two lanes to scalar registers
every two rows (ADR-0006), and a dictionary map that used a mispredicted branch to set a bit. A
single date predicate on its own — the `filter-string` query — now takes 2.4 ms in the filter
stage, against 16.5 ms before the branchless rewrite.

### 3a. The lazy scan's stagesThe same query, the lazy way. There is no filter stage, because the filter ran *inside* the
reader:

```
stage      rows in  rows out  elapsed
scan       6000000  315203    85.1 ms
project    315203   315203    0.0 ms
aggregate  315203   1         0.0 ms
```

The scan stage now carries the file's row count in and the surviving rows out, so the 5.7 million
rows the reader discarded are visible in the plan output rather than implied.

That is the **one-thread** scan. At six workers the same stage takes **16.2 ms**, and the plan
output says `read threads: 6` — the workers that ran, not the threads that were asked for, because
the file's six row groups are the cap. See [§2e](#2e-the-thread-count-sweep).

### 3b. The real Q6's stages, and what the arithmetic costs

The real Q6 has one more stage, and it is the one this increment added:

```
stage      rows in  rows out  elapsed
scan       6000000  407082    140.2 ms
filter     407082   110915    0.2 ms
project    110915   110915    0.8 ms
evaluate   110915   110915    0.2 ms
aggregate  110915   1         0.1 ms
```

**The `evaluate` stage is 0.2 ms of a 142 ms query — 0.14%.** That is the whole cost of the
arithmetic aggregate, and it is small for a reason that was a design decision rather than an
accident: the expression is evaluated over the **110,915 rows that survived the filter**, not
over the 6,000,000 rows of the file. SQL applies `WHERE` before the aggregate, and so does this.

The scan is 140.2 ms because the real Q6 reads `l_extendedprice`, which is the biggest column
in the file. **The cost of the real Q6 is the cost of reading a column, not the cost of
computing with it** — and that is why there is no vectorised arithmetic kernel in this
increment. See [ADR-0012](docs/adr/0012-arithmetic-expression.md).

### 3c. The same query, on six workers

The plan output reports the workers that ran, and the stages show what they did:

```
stage      rows in  rows out  elapsed
scan       6000000  6000000   0.0 ms
filter     6000000  110915    2.0 ms
project    110915   110915    0.8 ms
evaluate   110915   110915    0.2 ms
aggregate  110915   1         0.1 ms
read threads: 1
operator workers: 6 filter, 6 projection
```

**The filter stage falls from 7.3 ms to 2.0 ms — 3.6× from six workers.** The projection falls
from 1.3 ms to 0.8 ms, and the two stages that do not parallelise — `evaluate` and `aggregate` —
are unchanged, because they are not parallelised.

**The `evaluate` and `aggregate` stages do not move, and they are not going to.** `evaluate` is
0.2 ms and `aggregate` is 0.1 ms; together they are 0.3 ms of a 3.1 ms query. Parallelising the
aggregate is forbidden — `SUM` is not associative, and the answer must not depend on the block
boundaries — and parallelising the evaluation would mean slicing the columns into blocks, a copy
per column, to save a fraction of a millisecond.

**The answer is the same bits.** `group [] -> [Float(5526985127.48064)]`, one thread and six, and
the CLI's end-to-end test checks it against DuckDB's answer on the real file.

## 4. The defects this increment found

Nine, all found by measurement, all recorded with their before-and-after numbers in the ADRs
and in the commit history.

| | before | after | where |
|---|---|---|---|
| The kernel's mask accumulation | 4.81 G rows/s (0.84× the compiler) | 8.84 G rows/s (1.51×) | ADR-0006 |
| The global aggregate: a key vector and a hash lookup per row, for one group | `scan` 48.9 ms | `scan` 0.0 ms | `columnar-engine/src/operators/aggregate.rs` |
| The dictionary map: a mispredicted branch per row | `q6` filter 41.2 ms | `q6` filter 6.7 ms | `columnar-engine/src/operators/filter.rs` |
| The reader decoded each predicate column **twice**, once per predicate | `q6` cold 358 ms | `q6` cold 168 ms | `columnar-engine/src/lib.rs` |
| The Arrow-to-chunk conversion copied the dictionary's distinct values **per batch** — 1.8 million string allocations on the lazy path, 14.6 million on the eager one | `q6` cold 137 ms (lazy) · 1890 ms (eager) | `q6` cold 121 ms (lazy) · 1181 ms (eager) | `columnar-engine/src/dataset.rs` |
| The pushdown's mask went through Arrow's `BooleanBuilder`, whose per-element capacity check cost more than decoding the columns did | `q6` cold 137 ms | `q6` cold 126 ms | `columnar-engine/src/pushdown.rs` |
| The pushdown compared values **one row at a time**, in Rust, while the filter ran the SIMD kernel — 6.4× slower than the engine's own filter on the same four predicates over the same six million rows | `q6` pushdown 42.9 ms | `q6` pushdown 6.1 ms | `columnar-engine/src/pushdown.rs` |
| **The `--threads` flag never reached the operators.** The resident path passed `ExecOptions::default()`, whose `threads` is `None`, and `None` means one thread — so the operators could not have been parallel through it, however much the code had been parallelised | no scaling at all: 13.8 ms at one worker and 13.8 ms at six | `q6` filter: 6.9 ms at one worker, **2.0 ms** at six | `columnar-cli/src/main.rs` |
| The serial filter **copied** the chunk's validity mask where it used to borrow it, because the parallel path needed a block's own copy | one copy of the whole mask per predicate | a borrow | `columnar-engine/src/operators/filter.rs` |

The global aggregate is the one worth calling out from the first increment: the module
documentation promised that `COUNT(*)` was an in-place fast path that reads no column, and it did
read no column — but it still allocated a key vector and did a hash-map lookup for every one of
the six million rows, in order to arrive at the same answer every time. The fix is a separate
path for the global case, where there is exactly one group and there never was a key.

The last three are from this increment, and they are the same kind of defect: work done per
batch, per predicate or per dictionary, where the shape of the problem does not need it. The
reader decodes a column once per projection mask that mentions it, so two predicates on one
column means two decodes — they are now pushed as one. The conversion was copying the
dictionary's distinct values out of every batch to merge them, when the merge is a lookup and
needs no copy. And the mask was being built through a builder whose per-element capacity check
costs more than the comparison it was carrying, when the mask is a bit vector and can be written
a word at a time.

The final figure for that one, on the published median of three runs, is **84.4 ms** — after the
pushdown was rewritten to run the engine's kernel, which is the next row.

One of the three turned out to be worth more than the increment that found it. The dictionary copy
was invisible on the path spec 002 was building, because the lazy path never materialises the
column — and it was worth 1.60× to the path it was not building, because the eager path
materialises all sixteen columns across 5,860 batches. See [§2b-bis](#2b-bis-the-eager-path-got-faster-too-and-it-is-measured).

The last one is the same kind of defect, found the same way: **a total that was never
attributed**. The scan's 121.5 ms was never split into the reader's decode and the comparison,
and the comparison turned out to be 42.9 ms of it — the larger half of the single-column scans,
and 6.4× slower than the engine's own filter on the same work. A total is not an explanation,
and the plan output now says which half is which.

## 5a. The performance gate

The constitution requires two gates — no statistically significant regression against a stored
baseline, and absolute budgets met — and until spec 004 neither existed. They do now, and they
are worth describing because of what they found.

`just perf-gate` measures the kernel, 32 independent blocks of 5 timed passes each, and compares
the samples against `bench-results/kernel-baseline.json` with a **Mann-Whitney U test**: the
exact permutation distribution for small samples, the normal approximation with tie and
continuity corrections for large ones. It is one-sided, in the direction "the current sample is
slower".

**The first version was statistically correct and useless.** Five consecutive runs against an
unchanged baseline produced:

| flavor | runs reporting a regression | the difference |
|---|---|---|
| `cpp-auto` | 5 of 5 | 1.3% – 2.3% slower |
| `cpp-simd` | 4 of 5 | 1.7% – 3.9% slower |
| `scalar` | 4 of 5 | 0.9% – 1.2% slower |
| `rust-simd` | 0 of 5 | — |

**Thirteen false positives in twenty checks, on code that had not changed.** The test was not
wrong: the machine's throughput drifts by a percent or two between one moment and the next, and
a test with 32 samples on each side detects that drift as significant every time.

So a regression now has to be **both** statistically significant **and** practically significant,
and the practical threshold is set from that measurement: **5%**, above the observed drift of
0.9%–3.9%. With it, five consecutive runs on unchanged code produce **zero** failures, and the
differences that remain are reported as *within the noise* rather than hidden.

The gate has four answers — no regression, within the noise, regression, and **inconclusive** —
and the last one is not a pass. It says the gate could not tell, which is more useful than a pass
that was decided by a threshold nobody examined.

## 6. Reproducing this

```bash
just dataset       # 6,000,000 rows, deterministic, about 2.8 seconds
just bench         # the kernel A/B -> bench-results/kernel.json
just compare       # DuckDB and Polars  -> bench-results/compare.json

just check-x86     # compile the x86-64 half of the kernel, from this ARM64 Mac
just verify-avx2   # run the AVX2 path under Rosetta 2 and check it against the oracle

python3 scripts/medians.py   # the published table, derived from the committed reports

just perf-gate      # the performance gate: measure, and compare against the baseline
just perf-baseline  # rewrite the baseline from a fresh measurement
```

`just compare` needs `DuckDB` on `PATH` or in `tools/bin/`, and the `polars` Python package
installed. Both versions are recorded in the report.

The comparison harness measures the load and the query separately, takes the **median** of the
timed runs, and **cross-checks every answer against the engine's own**. The `SUM` over 555,594
rows differs in the last bits between systems — floating-point addition is not associative and
the engines sum in different orders — so the check uses a relative tolerance rather than exact
equality.

To publish a table, run `just compare` at least three times, keep the reports, and derive the
medians with `scripts/medians.py`. The three reports behind the table in §2 are committed as
`bench-results/compare-run1.json`, `compare-run2.json` and `compare-run3.json`.

## 7. How to read this file

The framing rule for this project is **"kernel X on query Y"**, never "this database versus
DuckDB". A number here is a statement about *one operation on one query on one machine*, and it
is only meaningful next to its conditions.

So: the comparison kernel on the Q6 predicate set is 1.50× faster than the compiler's own
vectorisation of the same loop, and 2.50× faster than a genuinely scalar reference, on an M4 Max
with NEON, single-threaded, over 20 million rows. The engine's filter on the Q6 predicate set
takes 6.7 ms. The engine's lazy scan of the same file, reading the two columns Q6 needs and
pushing the predicates into the reader, takes 83.2 ms — against 31.0 ms for DuckDB and 187.8 ms
for Polars, and against 1277.8 ms for the engine's own eager read. The lazy path is 2.3× faster
than Polars and 2.7× slower than DuckDB, and the reason it is slower is measured and named: DuckDB
gets 3.2× from fourteen cores on the identical work, and the engine gets 5.0× from six — which
narrows the gap to 1.6×.
