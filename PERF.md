# PERF.md — the measured numbers, and the conditions they were measured under

Every number in this file was produced by `just bench` and `just compare` on the machine
described below, and the raw JSON is in `bench-results/`. Nothing here is estimated, extrapolated
or carried over from another machine.

**The tables below are derived, not typed.** The engine's comparison table is the median of
three full `just compare` runs, and the derivation is a checked-in script:

```bash
python3 scripts/medians.py
```

All three raw reports are committed, so the published figures can be re-derived by a reader
without re-running a benchmark. See [`bench-results/README.md`](bench-results/README.md).

## 1. The comparison kernel

**What is measured:** one pass over a column of `f64` values, comparing every row against a
threshold and writing a bit mask. 20,000,000 rows, column `l_discount`, operator `>=`,
threshold `0.04`. Median of 8 runs.

### Two baselines, not one

| flavor | what it is | rows/sec | ns/row | vs scalar | vs cpp-auto | matches |
|---|---|---|---|---|---|---|
| `scalar` | the C++ reference compiled with `-fno-vectorize` | 3.48 G | 0.288 | 1.00× | 0.60× | 12,726,115 |
| `cpp-auto` | **the same source**, compiled with ordinary flags | 5.75 G | 0.174 | 1.67× | 1.00× | 12,726,115 |
| `cpp-simd` | the hand-written NEON kernel, over the C ABI | 8.73 G | 0.115 | 2.50× | **1.50×** | 12,726,115 |
| `rust-simd` | the Rust `std::arch` intrinsics kernel, no FFI | 8.72 G | 0.115 | 2.51× | 1.51× | 12,726,115 |

**The spread, because a benchmark that only publishes its best numbers is not a benchmark.** Over
the 8 runs: `scalar` 2.80–3.51 G, `cpp-auto` 5.45–5.90 G, `cpp-simd` 7.56–8.83 G, `rust-simd`
4.77–8.93 G. This machine is not isolated, and single runs occasionally drop — the `rust-simd`
low of 4.77 G is one such run, in which every flavor was slower than its own median. The median
is the number to quote; the range is the noise floor.

**These numbers reproduce.** An earlier session measured the same kernel on the same machine and
got `scalar` 3.51 G, `cpp-auto` 5.87 G, `cpp-simd` 8.81 G, `rust-simd` 8.77 G — within 2% of the
medians above, and with the same `2.51×` and `1.50×` ratios. Two independent 8-run sets agreeing
to 2% is a stronger claim than either set alone.

Every flavor agrees on the match count, and the differential tests compare the **masks bit for
bit**, not just the counts.

### What the two ratios mean

- **`scalar → cpp-simd` is 2.50×.** This is how much vectorisation is worth, measured against a
  reference that really is scalar. It is checked against the disassembly: the `-fno-vectorize`
  object contains **zero** vectorised loop instructions, and the ordinary object contains ~300.
- **`cpp-auto → cpp-simd` is 1.50×.** This is the one that decides whether the hand-written kernel
  earns its complexity: it beats what clang produces from the same loop by half.

The first version of this table published one ratio, against a baseline that clang had
auto-vectorised. It was measuring two vectorised implementations. See
[ADR-0006](docs/adr/0006-auto-vectorised-baseline.md).

### The FFI seam

`cpp-simd` crosses a C ABI; `rust-simd` does not. They are within **0.2%** of each other — 8.73 G
against 8.72 G — against a run-to-run spread of a few percent. The seam is free. See
[ADR-0003](docs/adr/0003-cpp-ffi-seam.md).

### AVX2 correctness (verified on an ARM64 Mac)

**This is not a performance claim.** It is the answer to "this machine has no AVX2", and the answer
turned out to matter more than expected.

The project has two SIMD paths: NEON, measured above on this machine, and AVX2, for x86-64. The
development hardware is an ARM64 MacBook, so the AVX2 half could not be *timed* here — and, when
somebody finally tried to cross-build it, it turned out it could not be *compiled* either. The
AVX2 Rust intrinsics path had never been built by anyone. It had two type errors in it (`u32`
accumulated into a `u64` mask), and it had been sitting in the tree, unchecked, for the entire life
of the project. See [ADR-0009](docs/adr/0009-avx2-without-x86-hardware.md).

The fix has two halves.

**Compilation** is now gated. `just check-x86` cross-compiles the workspace for
`x86_64-apple-darwin` on this machine, and CI runs the same check. The AVX2 path cannot rot
unnoticed again.

**Correctness** is now testable here, because Rosetta 2 executes AVX2 instructions correctly on
Apple Silicon while reporting *no* AVX2 in CPUID — the host is an ARM64 chip, so the feature bits
say so. The kernel's runtime probe therefore correctly concludes that there is no AVX2 path and
never enters it. `COLUMNAR_FORCE_SIMD=avx2` overrides the probe, which is what `just verify-avx2`
does:

```
$ just verify-avx2

-- without the override --
    forced        : auto
    simd_kind     : none
    avx2 rows     : 0
    matches oracle: true

-- with COLUMNAR_FORCE_SIMD=avx2 --
    forced        : avx2
    simd_kind     : avx2
    avx2 rows     : 1024
    matches oracle: true

RESULT: PASSED -- 3 test binaries green under Rosetta 2 with AVX2 forced.
```

The `avx2 rows` counter is the load-bearing part. A dispatch that *reports* the AVX2 path is not
proof that the path's instructions ran; the counter moves only if they did, and the mask it
produced is compared against the oracle's bit for bit. So the claim is narrow and specific: **the
AVX2 path — both the C++ FFI path and the Rust intrinsics path — compiles, executes, and produces
masks identical to the oracle's, on an ARM64 Mac.**

**What this does not establish: any AVX2 performance number.** Under Rosetta the instructions are
emulated, so a timing taken there measures the translator, not hardware. The benchmark harness
therefore *refuses to measure* while the override is in force — `just bench` exits with an
explanation rather than producing a number that means something other than what it appears to mean.
AVX2 timings require an x86-64 machine with AVX2, and are published only from one. See
[Not measured](#not-measured).

## 2. The engine, against DuckDB and Polars

Five queries, each measured twice: **resident** (the data is already in memory) and **cold** (the
Parquet file is read as part of the measurement). Both incumbents answer the same question in the
same mode, and every answer is cross-checked against the engine's.

The queries:

| name | what it is |
|---|---|
| `scan` | `SELECT count(*)` over every row |
| `filter-numeric` | one numeric predicate, `l_discount >= 0.04` |
| `filter-string` | one predicate on the dictionary-encoded `l_shipdate` |
| `filter-range` | two numeric predicates `AND`ed, and a `SUM(l_quantity)` |
| `q6` | the TPC-H Q6 predicate set: two numeric and two date predicates, `AND`ed |

### 2a. Resident — the data is already in memory

The like-for-like comparison: all three systems hold the data in memory and answer the query.

| query | **engine** | duckdb | polars | |
|---|---|---|---|---|
| `scan` | **0.0 ms** | 1.0 ms | 0.2 ms | engine wins |
| `filter-numeric` | **3.5 ms** | 15.0 ms | 12.1 ms | engine wins |
| `filter-string` | **3.5 ms** | 33.0 ms | 40.5 ms | engine wins |
| `filter-range` | 17.5 ms | 25.0 ms | **15.9 ms** | polars wins, engine 1.10× slower |
| `q6` | **11.3 ms** | 46.0 ms | 70.5 ms | engine wins |

**The engine wins four of the five, and loses one.**

The loss is `filter-range`, and it is not a filter problem. That query's stages are: filter
1.6 ms, project 7.3 ms, aggregate 2.2 ms. The engine materialises the projected column and then
sums it; `Polars` streams the sum over the selection without materialising anything. The pinned
optimization order says "late materialization", but the projection and the aggregate are two
separate stages rather than one fused operator, and the gap is the materialisation.

**The engine's query is 4.1× faster than `DuckDB`'s** (11.3 ms against 46.0 ms, resident) and 6.2×
faster than `Polars`'s. The lazy path does not change this: it reads the file *during* the query,
so it has no resident form and does not compete in this table.

### 2b. Cold — read the Parquet file and answer in one go

The engine is measured **twice** here. The **eager** path decodes every column of the file before
the query starts. The **lazy** path reads only the columns the plan needs, with the plan's
predicates pushed into the Parquet reader, so it has no resident form: its number is a cold number
by construction.

| query | **engine** (eager) | **engine** (lazy) | duckdb | polars |
|---|---|---|---|---|
| `scan` | 1202.6 ms | **0.1 ms** | 2.0 ms | 1.0 ms |
| `filter-numeric` | 1245.5 ms | **21.1 ms** | 22.0 ms | 45.4 ms |
| `filter-string` | 1211.5 ms | 31.9 ms | **23.0 ms** | 171.3 ms |
| `filter-range` | 1328.1 ms | 101.7 ms | 33.0 ms | **17.0 ms** |
| `q6` | 1267.8 ms | 89.1 ms | **32.0 ms** | 191.1 ms |

**The lazy path is 14.2× faster than the eager one on `q6`, and it turns a 39.6× gap against DuckDB
into a 2.8× one.** It beats Polars on every cold query except `filter-range`.

**It also beats DuckDB on `filter-numeric`** — 21.1 ms against 22.0 ms — which is the first cold
query the engine wins against DuckDB on this file. It is a narrow win, inside the noise of
DuckDB's own spread (22.0 to 34.0 ms across the three runs), and it is published as what it is:
a tie the engine takes, on one query, by a margin smaller than the machine's noise.

**The `scan` row deserves its own note.** `SELECT count(*)` needs no columns at all, so the lazy
path reads no column — it answers from the row count in the Parquet footer, in 0.1 ms. That is
faster than DuckDB's 2.0 ms and Polars' 1.0 ms, on the same file. It is also the narrowest
possible win, and it is in the table because the table is the table: a query that reads no data
should be fast, and here it is.

The two engines' answers are identical, row for row — the comparison harness refuses to report if
they are not — and so are the answers of all three systems, cross-checked at a relative tolerance
of 1e-9.

### 2b-bis. The eager path got faster too, and it is measured

Spec 001 recorded the eager path's cold `q6` at **1921 ms**. It is now **1181 ms** — 1.6× faster
— and the cause is not the machine being quieter. It is a defect that spec 002 fixed on the way
to building something else.

Both paths share one decode function. That function used to copy a dictionary column's distinct
values out of *every batch* to merge them, when the merge is a lookup and needs no copy. The lazy
path never paid it: it does not materialise the dictionary column at all — the pushed predicate is
evaluated on Arrow's array directly, and the plan reports `materialised columns: (none)` — so the
copy never happened there. The eager path pays it in full: it materialises all sixteen columns,
its reader hands the file over in 5,860 batches, and every one of them copied 2,500 distinct
strings. About 14.6 million string allocations, to build a dictionary of 2,500 entries.

Putting the copy back, deliberately, and re-measuring, gives the numbers rather than the story:

| | eager `q6` cold | lazy `q6` cold |
|---|---|---|
| with the per-batch copy | **1889.9 ms** | 119.0 ms |
| without it | **1181.1 ms** | 121.5 ms |

The eager path is 1.60× faster. The lazy path does not move — 119.0 against 121.5 ms is inside
its 2.6% spread — which is the control that makes the attribution credible: the fix helps the
path that copied and leaves the path that did not.

Both columns are from the measurement set that preceded the pushdown rewrite, and they are the
figures that set was made of. The eager path's current published figure is 1202.5 ms and the
lazy path's is 89.1 ms; the eager path moved by nothing more than the machine's noise, and the
lazy path moved because spec 003 rewrote the pushdown.

The perturbed run is committed as
[`bench-results/experiment-dictionary-copy.json`](bench-results/experiment-dictionary-copy.json),
and it is **not** one of the three reports the published table is derived from.

### 2c. The lazy scan, and what it reads

The lazy path is the change spec 002 made. It does three things:

1. **It resolves the plan against the file's schema**, before reading anything, so an unknown
   column or a type mismatch is an error before a single row is decoded.
2. **It reads only the columns the plan needs.** The reader is handed a projection over the file's
   root columns; the bytes of the others are never fetched from the file.
3. **It pushes the plan's predicates into the reader**, so the rows that fail them are dropped
   during the scan rather than after it.

For `q6` that is **two columns of sixteen**:

```
columns read: l_discount, l_shipdate
pushed down: l_discount >= 0.04 and l_discount <= 0.07,
             l_shipdate >= '1994-01-01' and l_shipdate < '1995-01-01'
```

Per the Parquet footer's own metadata, those two columns are 3.0 MiB and 9.1 MiB compressed
across the file's six row groups — **12.1 MiB of the file's 231.6 MiB**, and 2.9% of its raw
bytes. `l_comment` alone, which the eager path decodes and throws away, is 50% of the raw bytes.

**The remaining 2.8× against DuckDB is not pruning. It is threads.** This was published as a
pruning gap once, and that was wrong; here is DuckDB's own plan for the same query on the same
file:

```
╭─ Table Scan ───────────────────────────────╮
│ Function: READ_PARQUET                      │
│ Filters: (l_discount >= 0.04) AND ...      │
│ Row Groups Scanned: 6 / 6                   │
│ 315,203 rows                               │
╰─────────────────────────────────────────────╯
Data Read: 12.3 MB
```

**6 / 6 row groups scanned, 12.3 MB read** — the same two columns, the same bytes the engine
reads. DuckDB prunes *nothing* here, because there is nothing to prune with: the file has no page
index. The generator writes `EnabledStatistics::Chunk`, so there are no per-page statistics, and
neither system can skip a page it has never been told about. The engine fetches every page of the
predicate's column because the `ArrowPredicate` path evaluates over the decoded batch — but so
does DuckDB, because there is no page index to select against.

What is left is throughput, and it decomposes cleanly:

| | engine | duckdb | ratio |
|---|---|---|---|
| **Reader speed**, same job: decode all 16 columns into memory | **1202.5 ms** | 1357.0 ms | **0.89×** — the engine is ahead |
| **Architecture**: read 2 columns and push the predicate down | 89.1 ms | 32.0 ms | 2.8× |

The reader-speed term that ADR-0008 recorded as **1.58×** is **gone** — the shared decode path and
the dictionary fix closed it, and the engine's full-file decode is now ahead of DuckDB's. The
whole of the remaining 2.8× is the architecture term, and the architecture term is mostly this:

| | duckdb, one thread | duckdb, fourteen threads |
|---|---|---|
| `q6` cold | **32.0 ms** | **10.0 ms** |

**DuckDB gets 3.3× from fourteen cores on exactly this work**, and the engine is single-threaded
by design, in this increment, because the comparison pins both incumbents to one thread to make
the comparison like-for-like. That pinning is the reason for the gap, and it is a decision this
repository made on purpose.

So the remaining 2.8× is approximately **parallel decode the engine has not implemented**, plus
the residue — which the engine's own plan output names, and which spec 003 shrank: the pushdown
was costing 42.9 ms of the scan, and now costs 6.1 ms.

### 2d. Where the cold time goes

| system | load (file → queryable) | subprocess wall clock |
|---|---|---|
| **engine** (eager, `Dataset::read_parquet`) | **1202.5 ms** | — (a resident process) |
| **engine** (lazy, `ParquetSource::open`) | **0.1 ms** | — (a resident process) |
| duckdb (`CREATE TEMP TABLE ... AS SELECT *`) | 1357.0 ms | 20.2 ms |
| polars (`pl.read_parquet`) | 1362.0 ms | 92.3 ms |

Several things are worth separating here.

**The lazy path's "load" is the footer.** 0.1 ms: the file's metadata, and nothing else. The data
is read during the query, which is why the lazy path has no resident form.

**The eager path's decode is slow, and it decodes too much.** 231.6 MiB in 1.20 s is about
193 MiB/s. That is the `arrow-rs` Parquet reader going through every column of every row group and
materialising all sixteen columns into the engine's own chunk format, eagerly, whether the query
needs them or not.

**The incumbents are pinned to one thread.** `Polars` reads the file in 1362 ms single-threaded
and in about 184 ms with all fourteen cores. That 7.4× is the price of comparing a one-thread
engine against a one-thread engine. It is the right price, but it belongs in the reader's
column, not the query's.

**The subprocess wall clock is not the query.** `DuckDB`'s command line client starts in about
20 ms; `Polars`' Python interpreter plus the `polars` import takes about 90 ms, which is more
than most of the queries in the table above. Both are excluded from the query figures — they come
from the tools' own timers — and both are reported here.

## 3. What the engine's own stages say

The plan output splits the engine's work by stage. For the Q6 predicate set, resident:

```
stage      rows in  rows out  elapsed
scan       6000000  6000000   0.0 ms
filter     6000000  315203    6.7 ms
project    315203   315203    0.0 ms
aggregate  315203   1         0.0 ms
```

The filter stage does four predicates over 6,000,000 rows. The numeric ones run through the SIMD
kernel at 8.7 G rows/s, which is 0.7 ms each. The two date predicates run through the dictionary
path — one comparison per distinct date, then a map through the indices.

**The kernel is no longer the bottleneck of this query.** That is the point of the project, and it
took two defects to get there: a mask accumulation that extracted two lanes to scalar registers
every two rows (ADR-0006), and a dictionary map that used a mispredicted branch to set a bit. A
single date predicate on its own — the `filter-string` query — now takes 2.4 ms in the filter
stage, against 16.5 ms before the branchless rewrite.

### 3a. The lazy scan's stages

The same query, the lazy way. There is no filter stage, because the filter ran *inside* the
reader:

```
stage      rows in  rows out  elapsed
scan       6000000  315203    89.1 ms
project    315203   315203    0.0 ms
aggregate  315203   1         0.0 ms
```

The scan stage now carries the file's row count in and the surviving rows out, so the 5.7 million
rows the reader discarded are visible in the plan output rather than implied.

## 4. The defects this increment found

Seven, all found by measurement, all recorded with their before-and-after numbers in the ADRs
and in the commit history.

| | before | after | where |
|---|---|---|---|
| The kernel's mask accumulation | 4.81 G rows/s (0.84× the compiler) | 8.84 G rows/s (1.51×) | ADR-0006 |
| The global aggregate: a key vector and a hash lookup per row, for one group | `scan` 48.9 ms | `scan` 0.0 ms | `columnar-engine/src/operators/aggregate.rs` |
| The dictionary map: a mispredicted branch per row | `q6` filter 41.2 ms | `q6` filter 6.7 ms | `columnar-engine/src/operators/filter.rs` |
| The reader decoded each predicate column **twice**, once per predicate | `q6` cold 358 ms | `q6` cold 168 ms | `columnar-engine/src/lib.rs` |
| The Arrow-to-chunk conversion copied the dictionary's distinct values **per batch** — 1.8 million string allocations on the lazy path, 14.6 million on the eager one | `q6` cold 137 ms (lazy) · 1890 ms (eager) | `q6` cold 121 ms (lazy) · 1181 ms (eager) | `columnar-engine/src/dataset.rs` |
| The pushdown's mask went through Arrow's `BooleanBuilder`, whose per-element capacity check cost more than decoding the columns did | `q6` cold 137 ms | `q6` cold 126 ms | `columnar-engine/src/pushdown.rs` |
| The pushdown compared values **one row at a time**, in Rust, while the filter ran the SIMD kernel — 6.4× slower than the engine's own filter on the same four predicates over the same six million rows | `q6` pushdown 42.9 ms | `q6` pushdown 6.1 ms | `columnar-engine/src/pushdown.rs` |

The global aggregate is the one worth calling out from the first increment: the module
documentation promised that `COUNT(*)` was an in-place fast path that reads no column, and it did
read no column — but it still allocated a key vector and did a hash-map lookup for every one of
the six million rows, in order to arrive at the same answer every time. The fix is a separate
path for the global case, where there is exactly one group and there never was a key.

The last three are from this increment, and they are the same kind of defect: work done per
batch, per predicate or per dictionary, where the shape of the problem does not need it. The
reader decodes a column once per projection mask that mentions it, so two predicates on one
column means two decodes — they are now pushed as one. The conversion was copying the
dictionary's distinct values out of every batch to merge them, when the merge is a lookup and
needs no copy. And the mask was being built through a builder whose per-element capacity check
costs more than the comparison it was carrying, when the mask is a bit vector and can be written
a word at a time.

The final figure for that one, on the published median of three runs, is **89.1 ms** — after the
pushdown was rewritten to run the engine's kernel, which is the next row.

One of the three turned out to be worth more than the increment that found it. The dictionary copy
was invisible on the path spec 002 was building, because the lazy path never materialises the
column — and it was worth 1.60× to the path it was not building, because the eager path
materialises all sixteen columns across 5,860 batches. See [§2b-bis](#2b-bis-the-eager-path-got-faster-too-and-it-is-measured).

The last one is the same kind of defect, found the same way: **a total that was never
attributed**. The scan's 121.5 ms was never split into the reader's decode and the comparison,
and the comparison turned out to be 42.9 ms of it — the larger half of the single-column scans,
and 6.4× slower than the engine's own filter on the same work. A total is not an explanation,
and the plan output now says which half is which.

| **`SUM` over a computed expression** | This increment's aggregate sums a column; it does not evaluate arithmetic over columns. | The Q6 comparison uses Q6's *predicate* with `count(*)`. The limitation is stated, not hidden. |
| **Hash join, sort, window functions, decimal, dates, nested types, GPU** | Out of scope for spec 001. | Listed in the spec's out-of-scope table. |

## 6. Reproducing this

```bash
just dataset       # 6,000,000 rows, deterministic, about 2.8 seconds
just bench         # the kernel A/B -> bench-results/kernel.json
just compare       # DuckDB and Polars  -> bench-results/compare.json

just check-x86     # compile the x86-64 half of the kernel, from this ARM64 Mac
just verify-avx2   # run the AVX2 path under Rosetta 2 and check it against the oracle

python3 scripts/medians.py   # the published table, derived from the committed reports
```

`just compare` needs `DuckDB` on `PATH` or in `tools/bin/`, and the `polars` Python package
installed. Both versions are recorded in the report.

The comparison harness measures the load and the query separately, takes the **median** of the
timed runs, and **cross-checks every answer against the engine's own**. The `SUM` over 555,594
rows differs in the last bits between systems — floating-point addition is not associative and
the engines sum in different orders — so the check uses a relative tolerance rather than exact
equality.

To publish a table, run `just compare` at least three times, keep the reports, and derive the
medians with `scripts/medians.py`. The three reports behind the table in §2 are committed as
`bench-results/compare-run1.json`, `compare-run2.json` and `compare-run3.json`.

## 7. How to read this file

The framing rule for this project is **"kernel X on query Y"**, never "this database versus
DuckDB". A number here is a statement about *one operation on one query on one machine*, and it
is only meaningful next to its conditions.

So: the comparison kernel on the Q6 predicate set is 1.50× faster than the compiler's own
vectorisation of the same loop, and 2.50× faster than a genuinely scalar reference, on an M4 Max
with NEON, single-threaded, over 20 million rows. The engine's filter on the Q6 predicate set
takes 6.7 ms. The engine's lazy scan of the same file, reading the two columns Q6 needs and
pushing the predicates into the reader, takes 89.1 ms — against 32.0 ms for DuckDB and 191.1 ms
for Polars, and against 1267.8 ms for the engine's own eager read. The lazy path is 2.1× faster
than Polars and 2.8× slower than DuckDB, and the reason it is slower is measured and named: DuckDB
gets 3.3× from fourteen cores on the identical work, and this engine has one thread.
