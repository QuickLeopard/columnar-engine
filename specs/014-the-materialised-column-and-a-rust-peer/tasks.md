## T1 — The materialised column, taken apart

- [x] The probe from spec 012 now measures **three** columns of the real Q6 with the same decomposition:
      `l_discount` (a predicate column, dictionary-encoded, eleven values, **4-bit** indices),
      `l_quantity` (a predicate column, dictionary-encoded, 4,901 values, **13-bit** indices) and
      `l_extendedprice` (the **materialised** column). The RLE decoder and the page walking moved to
      `crates/columnar-engine/examples/common/mod.rs`, so there is **one** decoder and two things to measure
      with it.
- [x] The decoder gained a **wide-word path**. At thirteen bits the bit-at-a-time path was four times slower
      than the parquet crate's, which made the probe the bottleneck instead of the thing it measures: the
      probe's decode of `l_quantity` fell from **39.55 ms** to **8.89 ms**, and the crate's is **7.92 ms**.
- [x] The probe's decoder is still **checked against the parquet crate's, bit for bit, over every value of
      every row group, before it measures anything**. The probe stops if they disagree.
- [x] The query is the **real Q6** (`q6-revenue`), through the engine's own lazy path, as a ladder: the
      predicates alone, the predicates and the price, the predicates and the discount, the predicates and
      both, and the whole query.
- [x] The **query definitions moved into the engine crate**. A query is a plan, and a plan belongs to the
      engine that executes it: the probe measures the real Q6, and it could not reach a plan that lived
      above it. The probe's "whole query" used to be a hand-built stand-in, and it called itself the whole
      query.

## T2 — The counterfactual: the same column, the other way

- [x] The probe writes each column again, the other way: a dictionary-encoded column written **plain**, and
      the plain column written **with a dictionary** and a dictionary page big enough to keep it. One of the
      two is a loss, and the probe measures which.
- [x] **The materialised column is plain, not dictionary-encoded.** 258 of its 300 data pages are plain, and
      the 42 that are not are the first pages of each row group, before the writer's one-megabyte dictionary
      page limit was reached. The file carries a **dead 1.05 MB dictionary page per row group** — 6,313,096
      bytes over the file, **2.6%** of it — that no reader ever reads.
- [x] **The dictionary is a loss for the materialised column**: written with one, the column is
      **47,499,582 bytes** against the file's **36,451,424**, and Arrow decodes it in **39.74 ms** against the
      plain column's **36.01 ms**. The writer's fallback was the right call.
- [x] **And a large win for the two predicate columns**: `l_discount` plain is **21.07 ms** against the
      dictionary's **3.95 ms** and 11,644,361 bytes against 3,023,401; `l_quantity` plain is **36.50 ms**
      against **5.40 ms** and 26,980,250 bytes against 9,904,661. The dictionary pays for a low-cardinality
      column and loses for a high-cardinality one.

## T3 — The curve over the size of the data

- [x] The real Q6 is measured at **three dataset sizes** — 6, 12 and 24 million rows — generated by this
      repository's own generator from the pinned seed 24001, with the scale factor, the row count and the
      byte count recorded in each manifest. The generator is **byte-deterministic**: scale factor one at seed
      24001 is `data/lineitem.parquet`, with the same SHA-256.
- [x] The curve publishes the **stages**, so a reader can see which stage bends, and the **cost per million
      rows**, which is the question a reader asking about the size axis actually has.
- [x] **Every incumbent is measured at every size**, in the same harness, on the same file, with the thread
      count pinned. A curve with only this engine's line on it is a curve with nothing to be compared against.

## T4 — The Rust peer

- [x] **DataFusion** reads the same file and answers the same SQL, with the thread count pinned, and its
      answer is compared with the engine's at the same relative tolerance the other incumbents are held to.
- [x] The peer is a **measuring instrument, not a dependency**: it lives in `tools/datafusion-peer/`, outside
      the workspace, with its own committed lock file, and it is built by `just peer-build` into `tools/bin/`.
      The engine's dependency graph does not move: `cargo deny`, `cargo test --workspace` and the published
      dependency list never see it.
- [x] The peer speaks the harness's **existing marker protocol** (`LOAD_MS=`, `QUERY_MS=`, `VALUE=`), so it is
      measured in the same two modes — cold and resident — as the other incumbents, and the harness's parser
      is reused rather than written twice.

## T5 — The publication

- [x] Every figure is the **median of three full campaigns**, with the spread, and the raw reports are
      committed: `bench-results/materialised-run{1,2,3}.json` and `bench-results/compare-run{1,2,3}.json`.
- [x] `scripts/medians.py` derives the tables, and `scripts/check-published-figures.py` guards the figures
      that are quoted.
- [x] **ADR-0021** records what was measured, whichever way it went.
- [x] The comparison table was **re-measured** with the peer in it, and the figures that moved are stated
      with their old and new values.

## What this increment did not do, and why

- **The engine's scan does not change.** This increment is evidence. The measurement found no defect in the
  engine's read path: the engine's materialisation of the column is **37.65 ms** against Arrow's decode of
  the same column at **36.01 ms**, so the engine is already within **4.4%** of the floor the Arrow stack
  sets. A defect would get its own spec, the way every other one has.
- **ADR-0018's non-goal stands.** Owning the Parquet reading would buy the engine the difference between
  Arrow's decode and the parquet crate's — **1.64 ms** on the materialised column, and **1.51 ms** on the
  predicate's — and it would cost the Parquet format's RLE decoder, which has to match the crate's bit for
  bit. The measurement does not reopen it; it says the same thing from the other side.
- **The peer is not a target.** `DataFusion` is never a dependency of the engine, the kernels or the
  benchmark harness.
- **The engine does not grow a SQL parser.** The peer is driven with the SQL the repository already publishes
  for the incumbents, and the engine keeps its own plan.
