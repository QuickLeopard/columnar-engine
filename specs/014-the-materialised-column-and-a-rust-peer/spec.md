# Spec 014 — The materialised column, and a Rust peer

**Status**: done
**Started**: 2026-10-26
**ADR**: [ADR-0021](../../docs/adr/0021-the-materialised-column-and-a-rust-peer.md)
**Predecessor**: [012-the-scan-does-not-expand-the-predicates-column](../012-the-scan-does-not-expand-the-predicates-column/spec.md)

## The problem

Spec 012's T3 measured the expansion of the RLE indices in the **predicate's** column, and refused the
increment that would have avoided it. The refusal left a bigger number than the one it was about.

The query's time is not the predicate's column. On the real Q6, the predicate's column is a few
milliseconds of it, and the rest is the **materialised** column — `l_extendedprice`, the column the
query actually asks for. Nobody has measured what that cost is made of, how it moves with the size of
the data, or how it compares with a Rust peer doing the same query over the same bytes.

Three things are missing, and all three are evidence rather than features:

1. **The decomposition.** The materialised column's decode is the query's dominant cost, and it has
   never been taken apart. The predicate's column's decode was taken apart in spec 012; the same
   instrument, on the same file, should be pointed at the column that matters more.
2. **The curve.** The repository publishes a thread sweep and a load sweep. It publishes no curve
   over the **size** of the data, which is the axis a reader cares about when they ask "what does
   this cost per row".
3. **The peer.** The incumbents are `DuckDB` and `Polars`: one C++ and one Rust-through-Python.
   There is no peer that is a **Rust engine reading the same Parquet with the same Arrow stack**, and
   that is the peer whose number a Rust engineer can act on.

## The requirements

### R1 — The materialised column's decode is measured with the same instrument

- [x] The probe from spec 012 measures **three** columns of the real Q6 — the two predicate columns
      that are floats (`l_discount`, `l_quantity`) and the materialised column (`l_extendedprice`) —
      with the **same** decomposition: the parquet crate's decode, Arrow's decode, the probe's decode,
      the indices alone, the expansion, and the same column written the other way.
- [x] The query is the **real Q6** (`q6-revenue`), run through the engine's own lazy path, so the
      numbers are comparable with the published tables and the plan's stages are the engine's.
- [x] The contrast is published, and it is not the one this spec expected. The expectation was that
      the **materialised** column would be dictionary-encoded, so that its expansion would be the
      query's output's input and could not be avoided by comparing a dictionary instead. **It is not
      dictionary-encoded**: 258 of its 300 data pages are plain, and the writer abandoned its
      dictionary at the one-megabyte page limit. So the contrast is sharper than the one predicted —
      the materialised column has **no expansion to avoid at all**, and the counterfactual (the same
      column written *with* a dictionary) is **30% bigger and 10% slower**. The measurement says what
      each is worth: the materialised column is **58% of the query** and its cost is **bytes**.
- [x] The probe's own decoder is still checked against the parquet crate's, **bit for bit**, over
      every value of every row group, before it measures anything. It also had to be made **fair**:
      at thirteen bits the bit-at-a-time path made the probe four times slower than the crate, so the
      probe was measuring itself.

### R2 — The size curve

- [x] The real Q6 is measured at **several dataset sizes**, generated by this repository's own
      generator from a pinned seed, with the size recorded in the manifest. Three sizes: 6, 12 and 24
      million rows, and the generator is byte-deterministic — scale factor one at seed 24001 is
      `data/lineitem.parquet`, with the same SHA-256.
- [x] The curve publishes the **stages**, not just the total, so a reader can see which stage bends,
      and the **cost per million rows**, which is the question the size axis is asked for. The answer
      is that the cost per row is **flat** — 11.1, 11.6, 11.7 ms a million rows — which is what
      "the cost is bytes" predicts.
- [x] The **incumbents are measured at every size**, in the same harness, on the same file, with the
      thread count pinned. A curve with only this engine's line on it is a curve with nothing to be
      compared against, and the repository does not publish those.

### R3 — A Rust peer

- [x] A **Rust** query engine reads the **same file** and answers the **same SQL**, with the thread
      count pinned to the engine's, and its answer is compared with the engine's. `DataFusion` 49.0.2
      through Arrow 55.2.0: **1.9× slower** than the engine cold on the real Q6, and 3.6× slower
      resident.
- [x] The peer is a **measuring instrument**, not a dependency: it lives outside the workspace, so
      the engine's dependency graph is unchanged, and its own lock file is committed.
- [x] The peer is measured in the **same harness** as the incumbents, in the same two modes, and its
      numbers are published with the same conditions.

### R4 — The publication

- [x] Every figure is the **median of at least three full runs**, with the spread, and the raw
      reports are committed and derivable by `scripts/medians.py`.
- [x] `scripts/check-published-figures.py` guards the figures that are quoted.
- [x] ADR-0021 records what was measured, whichever way it went. The comparison table was
      **re-measured** with the peer in it, and the figures that moved are published with their old
      and new values.

## The non-goals

- **The engine's scan does not change.** This increment is evidence. If the measurement finds a
  defect, that defect gets its own spec, the way every other one has.
- **The peer is not a target.** `DataFusion` is never a dependency of the engine, of the kernels or
  of the benchmark harness. It is a separate project under `tools/`, built separately, and the
  engine's published dependency graph does not move.
- **The engine does not grow a SQL parser.** The peer is driven with the SQL the repository already
  publishes for the incumbents, and the engine keeps its own plan.
- **No new query.** The curve and the peer are the **real Q6** (`q6-revenue`), which is already
  published, so every number here is comparable with §2 and §3.
