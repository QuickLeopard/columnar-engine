# Spec 015 — Tasks

**Spec**: [015-the-row-group-count-is-a-knob](spec.md)
**ADR**: [ADR-0022](../../docs/adr/0022-the-parallelism-above-the-row-group-count.md)
**Predecessor**: [014-the-materialised-column-and-a-rust-peer](../014-the-materialised-column-and-a-rust-peer/tasks.md)
**Status**: done

## T1 — The knob

- [x] **The generator takes the row-group size.** `columnar-testdata` gained
      `generate_with_row_groups(spec, output, row_group_rows)` and the writer's properties take it, so the
      row-group size is a parameter and not a constant.
- [x] **The manifest records it, and the number of row groups written.** `DatasetManifest` carries
      `row_group_rows` and `row_groups`, and the row-group count is counted from the row count and the
      row-group size rather than read back from the file.
- [x] **The command line exposes it, and the default does not move.** `columnar-cli dataset
      --row-group-rows N`, defaulting to `ROW_GROUP_ROWS` = 1,000,000, so every published figure stays
      reproducible by the command that made it. `just dataset-row-groups N` wraps it and names the file
      after the row-group count it has.
- [x] **The report says how many row groups the file had.** `DatasetReport.row_groups` is in the
      benchmark report and in the sweep report, so a sweep says how many row groups the file it swept
      had, and the row-group count is not only in the prose.
- [x] **The `DataFusion` peer joined the sweep**, so a sweep has all three incumbents at every thread
      count and not two of the three. The older sweeps are published as they were measured.

## T2 — The measurement

- [x] **Three files, one session.** Six, twelve and twenty-four row groups, the same six million rows,
      the same seed, the same schema, generated by this repository's own generator.
- [x] **The engine and every incumbent swept at the same thread counts**, in the same harness, on the
      same file, with the answers cross-checked at every point — the same symmetry rule as every other
      sweep.
- [x] **The workers that ran are recorded against the threads asked for**, so the cap is visible in the
      table and not only in the prose.
- [x] **The campaigns are interleaved**, so a difference between the files is a difference between the
      files and not a difference between two times on a shared machine. Three campaigns of each, raw
      reports committed.
- [x] **The `q6` sweep was re-measured** on the six-row-group file, so the peer is in it and so the
      three files' numbers come from one session. The old figures and the new ones are both published.

## T3 — The confound, measured rather than assumed

- [x] **The same probe ran on all three files**, and the three files' shapes are published side by side:
      the encoding, the page mix, the dictionary-page bytes, the data-page bytes and the decode.
- [x] **The encoding is separated from the parallelism.** The materialised column's decode moves by 7%
      and its share of the query by 3%, while the predicates' cost moves by 56%. The encoding is a
      real effect and a small one.
- [x] **The incumbents are the control.** They read the same bytes, and their figures do not move:
      DuckDB 32.0 / 29.0 / 30.0 ms, Polars 189.4 / 186.6 / 190.3 ms, DataFusion 35.2 / 36.6 / 39.0 ms.
      So the engine's read got slower, not the file.
- [x] **The cost has a rate, not only a difference.** Three files give the rate: **0.85 ms** and
      **0.82 ms** a row group from the sweep, **0.81 ms** a row group from the probe's different query,
      and the rate does not scale with the number of columns the query reads.

## T4 — The publication

- [x] **Every figure is the median of three full campaigns**, with the spread, the raw reports committed
      and the tables derived by `scripts/medians.py`.
- [x] **`scripts/check-published-figures.py` guards the figures that are quoted** — the engine's number
      at each end of each file's sweep, the worker counts, the speedups, the probe's ladder and the
      incumbents' control figures.
- [x] **The wrong sentence in §2e is corrected.** It said *larger* row groups would go further; the
      read splits the row groups, so *smaller* ones do. The correction states the rule
      (`min(threads, row_groups)`) and points at the measurement.
- [x] **§5's row moves from "not measured" to "measured"**, with the numbers it rests on.
- [x] **ADR-0022 records what was measured, whichever way it went**, including the finding that the
      more parallel file is the slower one.

## What was not done, and why

- **The engine's read path was not changed.** This increment is evidence. The per-row-group cost it
  found is a defect, and a defect gets its own spec — see the ADR's decisions.
- **The mechanism of the per-row-group cost was not measured.** It is known to be per row group and not
  per column; it is not known whether it is the parquet crate's per-chunk setup, the dictionary read per
  column chunk, or something the engine does. That is the next spec's question.
- **The generator's writer was not changed.** The dead dictionary pages are a fact about the file, not
  about the engine — the same call ADR-0021 made.
- **The older sweeps were not re-measured.** The `q6-revenue` sweep, the resident sweep and the load
  sweep were measured before the peer joined the harness, and they are published as they were measured
  rather than re-run for the sake of a column.
