# Contributing

Thanks for reading. This repository is a measurement project first and a database second, and the
method is the contribution guide as much as the code is.

## The rules that are not negotiable

1. **Measure before you implement.** A performance claim in a pull request is a claim until a
   benchmark says otherwise. The repository's own numbers live in [`PERF.md`](PERF.md), and every
   one of them is the median of at least three full campaigns with the raw reports committed.
2. **No implementation without a spec.** The workflow is Spec Kit: **Specify → Plan → Tasks →
   Implement**. A change that touches the engine gets a spec under `specs/`, with requirements
   traced to a principle in [`constitution.md`](constitution.md), and an explicit out-of-scope
   table. The spec is written *before* the code.
3. **The evidence and the prose cannot drift.** Every published table is derived by
   [`scripts/medians.py`](scripts/medians.py) from the committed reports in `bench-results/`, and
   [`scripts/check-published-figures.py`](scripts/check-published-figures.py) fails the build if a
   quoted figure and the reports disagree. If you change a number, change the report it came from
   and re-derive it; do not edit the prose to match.
4. **A defect that is found is a defect that is published.** When a measurement finds a cost, the
   cost goes in the file with its before-and-after numbers, whether or not the fix lands in the
   same change.
5. **State old and new.** When a published figure moves, the old figure and the new one are both
   given, and the reason is named — including "the machine was busy", which is a real reason and
   has been a real reason more than once.
6. **Never guess an unmeasured number.** If something is not measured, it is listed in
   [`PERF.md` §5](PERF.md#5-not-measured) with the reason. It does not get an estimate.

## Getting set up

```bash
git clone https://github.com/QuickLeopard/columnar-engine
cd columnar-engine
just check          # the whole gate: fmt, clippy, tests, published figures
just dataset        # the published file: six million rows, deterministic from a seed
just demo           # run a query and read the plan output
```

Rust 1.97.1 or newer — the version CI pins to, so that a lint or a format difference is a diff to
review rather than a surprise failure. `just` is the entry point for everything; the recipes are
documented in the `justfile` and in [`PERF.md` §6](PERF.md#6-reproducing-this).

The dataset is **not** committed. It is a function of `(scale_factor, seed)` and is regenerated by
`just dataset`; the manifest says what it was, and `PERF.md` §2 states plainly that it is *not*
the official TPC-H SF-1 file.

## The gate

`just check` is the gate, and it is the same gate CI runs:

| gate | what it enforces |
|---|---|
| `cargo fmt --all -- --check` | formatting is never argued about |
| `cargo clippy --all-targets -- -D warnings` | workspace `all` + `pedantic`; no allowances |
| `cargo test --workspace --all-targets` | every test passes |
| `cargo deny check` | advisories denied, wildcards denied, `rand` denied |
| `scripts/check-published-figures.py` | every quoted figure agrees with the committed reports |

Two more checks matter on a machine that is not this one:

```bash
just check-x86     # the AVX2 half of the kernel, compiled
just check-wasm    # the browser's half of the kernel, compiled
```

The `simd128` path only exists in a `wasm32` build and the AVX2 path only compiles on x86-64, so
both rot silently on an ARM64 Mac unless they are compiled deliberately. Please compile them.

## Working on a performance change

1. **Write the spec.** `specs/NNN-what-it-is/`, with `spec.md` and `tasks.md`. Requirements traced
   to a principle; an out-of-scope table with reasons.
2. **Measure the thing you are about to change**, before you change it, and commit the reports.
3. **Change the code.**
4. **Re-measure**, three campaigns, interleaved, with the raw reports committed.
5. **Re-derive the tables** with `python3 scripts/medians.py` and paste them into `PERF.md`.
6. **Run the gate.** `just check` must be clean.
7. **Write the ADR** under `docs/adr/` if the decision cost something — an ADR here can retire a
   published figure, and that is the point of it.

If a measurement is taken on a busy machine, say so in the commit body and in
`PERF.md` §The conditions. The machine's drift is published rather than hidden, because a reader
who compares two sets needs to know why they differ.

## The benchmark workflows

The published numbers are not produced by CI. They are produced by two `workflow_dispatch`
workflows, and by hand, on a machine the repository does not own:

| workflow | what it measures | what it may publish |
|---|---|---|
| `bench.yml` | the kernel A/B on the NEON path, on a hosted macOS runner | **nothing** — a shared runner's absolute numbers are not reproducible |
| `bench-avx2.yml` | the kernel A/B on the AVX2 path, on a hosted x86-64 runner | **ratios only**, per processor |

Both are measurement workflows, so their toolchain floats: the report records it
(`machine.rustc`), which is what makes a figure attributable. The **gate** workflow, `ci.yml`, is
the pinned one — it installs **1.97.1**, the toolchain the published figures were measured with.

**The x86-64 ratios are published per processor, and that is not a detail.** GitHub's hosted
runners are a fleet: the twenty-one runs behind `PERF.md` §1b landed on six different processors,
and the ratio is a property of the processor as much as of the kernel. The rule the repository
follows is the same one it follows everywhere else, applied to a fleet instead of a host:

- group the reports by the machine that produced them;
- take the median **within** a group;
- publish a machine only if it ran **at least three campaigns**;
- name the machine, and never compare two machines' sets.

If you dispatch `bench-avx2.yml` and your run lands on a processor that has fewer than three
campaigns, its figures are **not** published — and that is the correct outcome, not a gap to fill
in with an estimate. Dispatch more runs.

`bench-avx2.yml` also has an `avx2-self-hosted` job, gated behind a `self_hosted` input. It needs
a runner with the labels `self-hosted`, `linux`, `x64`, and it is the only job whose **absolute**
figures would be worth publishing — because it would be a pinned machine instead of a shared one.
The gate is deliberate: a job that waits for a runner that does not exist leaves the whole run
queued for ever, so the default dispatch has to finish on its own.

## Style

- The house style is the clippy configuration: `all` + `pedantic`, `-D warnings`, and no
  `#[allow]` anywhere. If a lint needs suppressing, that is an ADR's worth of justification.
- `unsafe` is a last resort and is always documented with why it is needed and why it is sound.
- Comments explain *why*, not *what*. The code says what it does.
- No estimation of unmeasured numbers, in code or in prose.

## Reporting a bug

A bug report with a measurement in it is worth ten without. If you can reproduce it, the
repository's `just` recipes should reproduce it: say which recipe, which file, which commit and
what you got.

## Security

Please do not open a public issue for a security problem. Use GitHub's private vulnerability
reporting on this repository.
